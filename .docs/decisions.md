# Decisions

This log is for contributors who want to know why the toolkit is the way it is before changing it. Each entry gives the decision, the date, the reason and where it was made. Dates are UTC, taken from GitHub. Newer entries are at the end; an entry that a later one replaced says so.

## .NET 10 Native AOT on every platform, Linux built on Ubuntu 22.04

- **Date:** 2026-10-14
- **Partly superseded 2026-10-24** by "Players install `dmc`, which writes and updates a DMC folder": the clause "players install nothing but Claude Code" no longer holds (players install Claude Code and `dmc`). The rest of this entry stands.
- **Decision:** Replace the Python scripts and the two shell dice rollers with one .NET 10 program, `dmc`, compiled with Native AOT for each platform. Build Linux on Ubuntu 22.04. The floor for players is glibc 2.34. The self-contained single-file build stays as the local developer default only.
- **Reason:** Players then need nothing installed but Claude Code: no Python, no pip, no .NET runtime. .NET 10 is a long-term-support release. The Phase 0 spike found no AOT or trim warnings with the chosen libraries and start-up of 5 to 29 ms; single-file worked but started 15 to 20 times slower, which matters for a hook that runs before every message. An AOT binary runs only on the same or a newer Linux than it was built on, so Linux is built on the oldest Ubuntu runner, 22.04, which ships glibc 2.35. The 2.34 floor is not the runner's glibc but the newest glibc symbol version that `dmc` and its native libraries use, measured in the spike.
- **Source:** Issue #3 (plan and "Verified facts"), and its Phase 0 decision comment.

## One-line errors, and output kept small

- **Date:** 2026-10-14
- **Decision:** Every `dmc` failure is one line, `dmc <command>: <message>`, never a stack trace or the usage text. Output is UTF-8 with no byte-order mark and LF line ends. Each port kept its script's output exactly, apart from deliberate, listed differences.
- **Reason:** Everything `dmc` prints lands in DMC's context and is paid for in tokens. Identical output meant DMC read no more than before, and the prompts and tests depending on it kept working.
- **Source:** Issue #3 ("Keep errors to one line"); PR #8.

## Map scales of 5 ft and 30 ft, plus miles for overland maps; no 10 ft

- **Date:** 2026-10-14
- **Decision:** Every map is drawn to scale. `cell_ft` must be 5 (the default, the 5e grid), 30 (one turn of movement at speed 30, for fights and places too large for 5 ft squares), or 5280, 31680 or 316800 (1, 6 or 60 miles a square) for overland travel maps. `null`, 10 ft and any other value are refused. No rule ties token kinds to scales; that a fight never uses a mile scale is guidance in the `draw-map` skill.
- **Reason:** Sketch maps without a scale led to wrong distances in play and had to be redrawn mid-campaign. The plan in issue #3 expected a 10 ft scale; the user chose 5 ft and 30 ft instead, so both work for combat, and 30 ft is a choice made for this toolkit rather than a published scale. The mile scales follow the province, kingdom and continent scales of the Dungeon Master's Guide.
- **Source:** PR #5 and PR #7 (the pre-port step of issue #3).

## Map PNGs at 1:1

- **Date:** 2026-10-15
- **Decision:** `dmc map --png` draws the PNG at exactly the SVG's size. The Python renderer drew it at 4/3 of that.
- **Reason:** The PNG exists for DMC to look at, and an image costs tokens by its pixels. This was the one deliberate difference in the `map` port.
- **Source:** PR #9 ("user decision, to save image tokens").

## Intel Macs not built (superseded 2026-10-23 by "macOS is no longer supported")

- **Date:** 2026-10-15
- **Decision (superseded 2026-10-23: no `osx-arm64` build any more):** Releases are built for `win-x64`, `win-arm64`, `linux-x64`, `linux-arm64` and `osx-arm64`, not `osx-x64`.
- **Reason:** The plan made Intel Macs optional; it would be the one target that neither the tests nor the spike ever ran, and the Intel runner image is the last of its kind. Adding it later is one matrix row.
- **Source:** PR #14 ("RIDs").

## The release opens its own pin pull request

- **Date:** 2026-10-15
- **Superseded 2026-10-24** by "Releases are immutable and their checksums signed; `dmc update` and an install line replace the pin (issue #67)": the release workflow no longer writes a pin or opens a pull request, and `get-dmc` and `tools/dmc-release.json` are gone. The idea that nothing is published before every archive has been installed on its own platform stands.
- **Decision:** Pushing a `dmc-vX.Y.Z` tag on `main` is the only thing that publishes. The release workflow builds and installs every archive on its own platform before publishing, then writes `tools/dmc-release.json` from the published archives and opens the pull request that pins them. `get-dmc` checks every download against that pin's SHA-256 before running anything, and the launchers start Claude Code even when `dmc` cannot be had.
- **Reason:** A release and its pin cannot drift apart through a forgotten manual step, and a mismatch fails loudly instead of running the wrong program. Play must never depend on a download succeeding.
- **Source:** Issue #3 ("Build and release", "How a player gets `dmc`"); PR #14 and PR #15.

## Git rules for toolkit work in CLAUDE.md

- **Date:** 2026-10-15
- **Decision:** `CLAUDE.md` ends with a "Git and GitHub" section: never commit to `main`, one change per branch, never add personal or copyrighted folders, a full PR description checked after opening, `Part of #N` for a phase and `Closes #N` only for the last, one code review per PR, CI green before the user merges.
- **Reason:** The practice had lived only in session memory. A PR body had come out as `-`, earlier PRs named issue #3 with no keyword, and one PR had three full reviews. The section is short and last, so it costs little during play.
- **Source:** PR #10.

## The Python scripts deleted at the switch-over

- **Date:** 2026-10-17
- **Decision:** Once the first release was pinned, point `CLAUDE.md`, the skills, the settings and the README at `./bin/dmc`, and delete `scripts/` (the four Python scripts, both dice rollers, `requirements.txt`), the Python tests and the parity check that had compared each port with its script.
- **Reason:** Each phase had kept the old script running beside the new subcommand so play never broke halfway. The switch-over waited for the pin (PR #17), because without a release DMC would have had no dice roller. The parity check's inputs were kept as the error-path guard's case lists.
- **Source:** PR #16 ("Closes #3"), merged after PR #17.

## Keep the missing-`dmc` notice at session start

- **Date:** 2026-10-17
- **Reworded 2026-10-24** (issue #67): the notice stays, in the play settings that `dmc` writes (`kit/settings.json`), and now tells DMC that `dmc` is missing or does not run and to reinstall DMC with the install line in its README. **Reworded 2026-11-04** (issue #67, PR 3): a DMC folder has no README, which the first play test from a DMC folder showed (DMC searched for it and had to guess the SRD link), so the notice, `kit/dm-rules.md` and `dmc-setup-rules` now give the two install lines and the SRD links themselves. The DM rules no longer suggest `dmc update` for a missing `dmc`, since that needs a working `dmc`. It still runs `dmc --version` and prints nothing when `dmc` runs. **Reworded 2026-11-17** (issue #208, PR #233's code review): "so dice, maps and PDF reading will not work" implied the rest of play goes on, so the notice now says `dmc` is not found or will not start and DMC cannot play until it does, as `kit/dm-rules.md` § Dice says.
- **Decision:** Keep the `SessionStart` hook in `.claude/settings.json` that runs `bin/dmc --version` and, when it fails, tells DMC in one line to run `get-dmc` before the first roll.
- **Reason:** Without it, a session started with plain `claude` and no working binary relies on DMC acting on a line in `CLAUDE.md`, which it would usually do only after a roll failed. It costs one shell start per session and prints nothing when `dmc` runs. It does not run `get-dmc` itself, which would touch the network on every start.
- **Source:** PR #16 (proposed under "For the user to decide"); kept by the user's decision after that PR merged.

## Developer builds report `0.0.0-dev` and live in `artifacts/bin`

- **Date:** 2026-10-17
- **Partly superseded 2026-10-24** (issue #67): the parts about `bin/` being owned by `get-dmc`, the pin and the stale-binary warning are gone with them. A development build still prints `dmc 0.0.0-dev`, which no release has, so `dmc install` copies it as the program only with `--force` and `dmc update` refuses it.
- **Decision:** Every build that is not a release prints `dmc 0.0.0-dev`, a version no release has. Developers publish to `artifacts/bin/`; `bin/` is only the player's install, which `get-dmc` owns. The pin pull request no longer writes the project file's version, and the stale-binary warning ignores a development build.
- **Reason:** An old local build in `bin/` reported the release's version, so `get-dmc` kept it, and a newer subcommand failed with "unknown command". A version that can never match the pin makes `get-dmc` replace any stray build. Two earlier designs (a stamp file with the program's SHA-256, and a dev version sharing `bin/`) were dropped as costlier and incomplete.
- **Source:** PR #20.

## Combat procedure rules from issue #6, Phase 1

- **Date:** 2026-10-17
- **Decision:** Put the fixes for combat-procedure problems found in reviewed play sessions into the prompts and templates:
  - in a fight, narrate before redrawing the map, with distances from `dmc map --measure`, and stop when something the player relied on turns out wrong;
  - the combat tracker lists every enemy attack with its reach or range and what it needs, and DMC says what an enemy can do from that list;
  - "wait for X" is a readied action, said back before confirming; an agreed plan is checked once and written down, and companions follow it unasked;
  - a question in reply to a request for a go-ahead is not a yes;
  - every roll the options let the player see is shown as `dmc`'s line with a label, target and result;
  - the tracker records the current turn's movement and actions, who has acted and what is readied;
  - resume and the full save compare the game state with companions' sheets too.
- **Reason:** Each rule had first been written into one player's options file after a mistake, where no other player or campaign would get it. By the test in the `review-transcript` skill (would it be wrong for any player?), they are toolkit rules, so each got one home in `CLAUDE.md`, a skill or a template.
- **Source:** Issue #6; PR #19 ("Part of #6").

## Skip the Gatekeeper and SmartScreen checks

- **Date:** 2026-10-17
- **Decision (the Mac half is superseded 2026-10-23, as macOS is no longer supported):** Do not test an unsigned `dmc` on a fresh Mac (Gatekeeper) or a fresh Windows PC (SmartScreen, Defender) before relying on it. Deal with any such problem if it is reported.
- **Reason:** The user's call. Archives fetched by `curl` or `Invoke-WebRequest` are expected to carry no quarantine mark, and the release workflow runs every archive on its own platform's runner, but a runner is not a fresh consumer machine. Code signing stays out of scope unless a problem appears.
- **Source:** Left open in issue #3's Phase 0 comment and in PR #14 ("Still open"); the user's decision on 2026-10-17, given in a session rather than in an issue or PR.

## Every change updates its documentation

- **Date:** 2026-10-17
- **Decision:** `CLAUDE.md` § Git and GitHub requires every change to update the documentation in the same PR: an XML doc comment on every type and member added or changed (private ones included; the build catches only missing public ones, from PR #24), a header comment on every script and workflow, and the `.docs/` documents that describe the change, including `roadmap.md` and this log. A change to `CLAUDE.md`, a skill or a template counts. The PR description says which documents changed, or why none needed to, and the review checks the documentation is current.
- **Reason:** The user asked for everything to be documented in code and in product-level documents in `.docs/`, and for that to hold for every change from now on. `CLAUDE.md`'s git section is what all toolkit work, including subagents, follows, and it costs nothing during play.
- **Source:** PR #22.

## Labelled rolls: a natural 20 or 1 decides an attack only, and the old line is kept

- **Date:** 2026-10-17
- **Decision:** `dmc roll` takes `label:dice@AC<n>` or `@DC<n>` and prints the existing line with the label before it and the verdict after (`Pip, shot: 2d20kl1+5: [17, 9] keep [9] +5 = 14 vs AC 14, hit`). Against an AC, a natural 20 hits and a natural 1 misses whatever the total, only when exactly one d20 counts (a single d20, or the kept die under advantage or disadvantage), and the line says `(natural 20)` or `(natural 1)`. A DC gets no such rule, since 5e gives no automatic success or failure to checks and saves. Meeting the target succeeds. The line keeps the old format rather than the shorter one sketched in issue #6 (`... 2d20kl1+5 [17, 9] keep 9 +5 = 14 ...`), so the line is what `dmc roll` always printed and what Phase 1 already put in `CLAUDE.md`; the cost is a double colon after the label.
- **Reason:** Rolls went unshown when many came in one reply, because DMC rebuilt each line by hand. With `dmc` printing the whole line, DMC pastes it unchanged. The natural 20 and 1 rule is in the SRD for attack rolls only ("If the d20 roll for an attack is a 20, the attack hits regardless of any modifiers or the target's AC", and likewise a 1 misses).
- **Source:** Issue #6 finding 4; PR #25; SRD 5.1, "Making an Attack".

## Pasting `dmc`'s line unchanged, and house rules stated after it

- **Date:** 2026-10-17
- **Decision:** `CLAUDE.md` § Dice has DMC paste `dmc`'s line unchanged, one per roll. If a campaign's house rule changes a verdict, DMC pastes the line unchanged and states the ruling after it.
- **Reason:** The line is the record of what was rolled, and `dmc` follows strict 5e, so it cannot know a house rule. Editing the line would make it say something no die produced.
- **Source:** Review of PR #25.

## Turn order on the map: initiative by token id

- **Date:** 2026-10-17
- **Decision:** `live.json` takes optional `"initiative"` (the creatures in turn order) and `"current"`. Each entry is a token's `id`, preferred because ids are unique, or the name of exactly one token; a name shared by several tokens is refused with their ids. An entry that matches no token is an error, `current` must be in `initiative`, and both keys are checked only when drawing, so `--measure` is never blocked by a stale order. A scene does not inherit the keys from its base place. In a fight DMC sets `current` once per reply, in the same edit as any moves, and runs `dmc map` once, last, only if something on the map changed.
- **Reason:** The player lost track of whose turn it was and when each creature acts. Names need not be unique ("Goblin" twice), so matching by name alone drew the wrong token or none. An unmatched entry is an error so that a typo is caught instead of drawing silently; the cost is that a creature that is not a token (a lair action) cannot be listed. Redrawing once per reply, not once per monster turn, keeps the cost of a fight down.
- **Source:** Issue #6 finding 5; PR #25 and its review.

## The build checks that code is documented

- **Date:** 2026-10-17
- **Decision:** `Directory.Build.props` turns on `GenerateDocumentationFile`, so the compiler reports CS1591 (no XML comment on a visible type or member) and checks that comments are well formed. In `src/Dmc.Cli` that is a build error, through its existing `TreatWarningsAsErrors`. In `tests/Dmc.Tests`, comment correctness (CS1570 to CS1574, CS1580, CS1584, CS1587, CS1589, CS1590) is an error in every file, and CS1591 is an error except in the files that hold MSTest test classes (`*Tests.cs`, `*Contract.cs`, `*Cases.cs`), where `tests/Dmc.Tests/.editorconfig` turns it off. `PublishDocumentationFile` is false, so `dmc.xml` stays out of the publish output and the release archives. Private and internal members are documented too, but the compiler cannot check them.
- **Reason:** The user asked for everything to be documented in code, and for it to stay so; a check that fails the build is what keeps it. The test classes are the exception because MSTest needs public test methods, and a test whose name says what it proves needs no comment: checking them would have flagged 382 members meant to have none. Scoping the exemption by file, not switching CS1591 off for the whole test project, keeps `Support/`, the fixtures and `Bootstrap.cs` checked. The documentation file is kept out of publishing so the archives stay at the four files `release.yml` insists on.
- **Source:** PR #24.

## The break alert is relative to where the resume left the context

- **Date:** 2026-10-17 (amended 2026-11-16 by "The feedback round of #181": the bands rise every 50,000, the first still at the baseline plus 40,000; amended 2026-11-18 by "A typed resume sets the break baseline"; the text below is the original rule)
- **Decision:** `dmc context-check` starts its bands at the larger of 150,000 tokens and the session's baseline plus 40,000, then every 40,000 after that. The baseline is the context of the last call before the first player message in the part of the log after the latest compaction boundary (the end of the recap after `/clear` and `/resume-campaign`), else of the first reply to that message. It uses no resume marker, so it holds however the files were loaded, and a resume the player runs mid-session cannot move it up. Injected user records (interruptions, shell-command records, command echoes, system reminders) and every text block of a message are handled by one classifier shared with `dmc digest`. The size is read from the end of the log and the baseline from the start, parsing only what can settle it, so an 18 MB log costs about 20 ms over process start. 150,000 stays as the floor. A declined break is offered again at the next band, counted from the first one. The line says "Context 163k is large", and `CLAUDE.md` § Compaction suggests a break "when the context has clearly grown large" instead of "when a session has clearly run long".
- **Reason:** A flat 150,000 fired one or two messages after `/resume-campaign` in three play-test sessions, because a resume added 96,000 to 142,000 tokens. Taking the break then reloaded the same files and put the context back near the threshold. What a break saves is the conversation grown since the files were loaded, so that is what the alert measures. The player asked to change the alert rather than their own habits. The baseline comes from what the hook can read, the log. After a compaction the log keeps going, so only the part after the boundary counts, and `/clear` starts a new log. The cause is context size, not session length, so the wording says so.
- **Source:** Issue #35 and its numbers (sessions `65b51f17`, `a4c01d59`, `bb8f7d9a`).
## A lighter resume: canon is searched past the archive level, the session log is read from its tail

- **Date:** 2026-10-17
- **Decision:** `resume-campaign` reads `story/canon.md` whole only while it is under about 230 lines (counted with the Grep tool). Past that it reads two sections whole whatever the scene, **Rulings** and **Prices, debts and promises** (the sections whose omission causes contradictions), and searches the rest for the names, places and threads in `game-state.md`'s Scene block, Active quests and Pending lines. Timeline is searched, not always read: it is the largest section in the one campaign measured, not short. It reads the last three scenes of the latest session log (found by `### Scene N:` headings with a number, so the template's commented example is not counted), or the whole log when the last full save does not cover it (its stamp now ends "through scene N"). It reads sheets only for the PCs, the companions (a block under Party status) and the NPCs present; the game-state template and `update-game-state` gain a "With the party, not companions" block so that a rescued NPC or a guest is not read as a companion. `campaign-full-save` step 4 splits long canon lines, then counts and archives down to about 200, never moving the two always-read sections, and may keep a long canon when every subject is live; its consistency check re-counts. Resume never asks for live subjects to be archived. The numbers and the read rules live in the two skills; the canon template only marks the always-read sections.
- **Reason:** In the issue #6 Phase 3 play test a resume added 96,000 to 142,000 tokens. Step 7 said to read canon "all", which contradicted `CLAUDE.md` § Accuracy ("For a large `canon.md`, search it instead of reading it all"); the archive step at a full save was a conditional that was easy to skip; the latest session log was read whole (in one resume twice); and sheets of NPCs who were not in the scene were read. Measured on the real campaign by bytes divided by 4, the resume's file reads fell from about 76,300 tokens to about 54,500 to 59,300 (see the PR). The line count is a weak proxy for cost (this campaign's canon lines average over 300 characters), so the save also splits long lines. Rulings and promises are always read because a search by scene names would miss a house ruling or a debt that the current scene does not mention.
- **Source:** Issue #35; PR #40 and its review.
- **Superseded in part:** the 230 and 200 lines became token sizes measured by `dmc size`; see "Size rules are measured in tokens by `dmc size`".

## `dmc pdf` output is all or nothing, through a staging folder inside the output folder

- **Date:** 2026-10-17
- **Decision:** `text`, `render` and `all` make the output folder first, write into `<out>/.dmc-partial-<random>`, and move every file into place only when the whole run has succeeded, printing the report lines then. A page whose picture would be over 65,500 pixels on a side at the requested `--dpi` is refused up front, before anything is drawn or made. Before moving, the commit checks for the obstacles it can foresee (a file where a folder must go, a folder where a file must go) and refuses without moving anything. A failed run deletes the staging folder and every folder it made, item by item, and never deletes or replaces anything already in the output folder. If the clean-up fails, a line on stderr names the leftover folder; if the files were all moved but the staging folder cannot be deleted, the run still succeeds and says so after its report. A successful run still replaces files of the same name and leaves other files alone. `info` is unchanged. The code is `Pdf/OutputStaging.cs`; no test hook is in the binary.
- **Reason:** A run that failed on page 40 left pages 1 to 39 and the text files in `extracted/`, which looks like a finished extraction missing its last pages, and `ingest-module` could digest a book with pages missing. The staging folder is inside the output folder, not beside it (the first version put it beside), because then a run needs write access only where it writes, every move is a rename on one volume even if the output folder is a symbolic link or a junction, and an output path that cannot be used fails when the run starts, not after rendering. Moving file by file, not swapping folders, keeps the old merge behaviour and the promise that existing files survive a failed run. The size check is up front because it is the one failure that can be known before any work, and the tests had been using it to force a late failure; the late failure is now tested by an obstacle at the commit, which is real and needs no hook, and `OutputStaging` has its own unit tests.
- **Costs:** A re-run keeps its new files in the staging folder while the old ones are still in place, so it briefly needs disk space for both sets. The move is many renames, so a failure in the middle of it (the disk fills, a file is read-only) can still leave some files moved. A killed process, or a file another program holds open, can leave the `.dmc-partial-` folder behind; it is safe to delete, and the user is told where it is whenever the program is still running to tell them.
- **Source:** Issue #30; the review of PR #33.
## A bad token count is refused when the log is read, and stops the whole digest

- **Date:** 2026-10-17
- **Decision:** `Session` checks the token counts of every assistant record as it reads it: each of the four counts must be a number, and finite, and the context reading (input plus the two cache counts) must be finite. A record that fails is reported by the existing catch as `<file>.jsonl line N: <message>`, exit 1, like any other shape error. A bad log stops the whole run, `list` and `show` alike, before anything is printed or written; it is not skipped.
- **Reason:** A non-finite count had been found only when the statistics were worked out, after `Session` had finished, so it escaped as an unexpected failure, with earlier sessions' files already written, and `list` and `show` could disagree about the same log. Checking where the record is read fixes all of it at the root: one place, one message form with the line number, and `list` and `show` refuse exactly the same logs. A first version caught the error in a wrapper around the reporting; it was dropped as treating the symptom. Stopping rather than skipping follows from how `Session` already treated every other bad log, and a skipped session would leave `stats.md` quietly short of one and the `review-transcript` skill reading it as complete. `show` already read every session before writing, so no build-ahead of the output was needed.
- **Limits:** Sums across many calls are not checked: counts that are each finite but add up past about 1.8e308 would still fail in the statistics as an unexpected failure. No real log has such numbers.
- **Source:** Issue #29; the review of PR #32.
## No deleting campaign files in play

- **Date:** 2026-10-17
- **Decision:** `CLAUDE.md` § Saving as you go forbids deleting or moving a file under `adventures/` unless the player asks for that file to go, and then DMC tells the player the command to run themselves. `.claude/play-settings.json` adds deny rules: `Bash(rm *)`, `Bash(rmdir *)`, `Bash(unlink *)`, `Bash(mv *)`, `Bash(git clean *)`, `Bash(find * -delete*)`, `Bash(xargs rm*)` and `Bash(xargs * rm*)` (Claude Code strips a bare `xargs` but not one with flags), and for PowerShell `Remove-Item` and `Move-Item` with `rm`, `del`, `erase`, `rd`, `ri`, `rmdir`, `mi`, `move` and `mv`, plus `git clean`, each written out although Claude Code matches a cmdlet's aliases. `ToolkitTests.ThePlaySettingsDenyShellDeletes` checks that the rules are present, that they match the commands they should and not `./bin/dmc` or read-only commands, and that none of them is in `settings.json` (toolkit work). The rules are in play-settings only, so toolkit work can still delete files. The `rewind-campaign` skill, which used to delete maps of places the party had never seen, now treats the agreed rewind as the player's request, lists those maps, asks the player to confirm and gives the delete command; until they are gone it records them in `game-state.md` Pending as "do not load or draw" (read by `resume-campaign` and `draw-map`) and leaves them out of its clean-up sweep. It never empties a file with Write as a way to delete it.
- **Reason:** In the issue #6 Phase 3 play test (session `a4c01d59`) DMC ran `rm` on three git-ignored campaign files the player still needed, and they had to be rebuilt from a transcript. The prompt said not to use shell commands on campaign files but never said not to delete. Claude Code's documentation says a `*` in a Bash or PowerShell rule matches any text, that a trailing ` *` also matches the bare command (only when it is the rule's only wildcard), that deny rules apply when any subcommand of a compound command matches (so `cd x && rm y` is caught), that wrappers such as `timeout` and leading `VAR=x` assignments are stripped before matching, and that PowerShell matching is case-insensitive and canonicalizes aliases.
- **Limits:** A deny rule matches the command text Claude writes. It does not stop `/bin/rm` or `bash -c 'rm ...'` (the documentation's own examples), `powershell -c "Remove-Item ..."` or `cmd /c del` run from Bash, `find -exec rm`, `cp` or a redirect over a file, a redirect that truncates a file, or a script or interpreter (`python -c`) that deletes. The Edit and Write tools can still overwrite a file. A `mv` or `Move-Item` by another spelling (`/bin/mv`, `bash -c`) is forbidden by the prompt only. The block was not tried against a live Claude Code session: the attempt to run a nested session was refused by the harness, so the matching is taken from the documentation (https://code.claude.com/docs/en/permissions) and the toolkit test checks only the rules' text and the documented matching, not Claude Code's own parser. The prompt clause is the first line of defence; the rules catch the usual forms.
- **Source:** Issue #36; PR #38.

## The map is redrawn by a Stop hook after the reply

- **Date:** 2026-10-17
- **Decision:** DMC no longer runs `dmc map` to redraw during a fight. It edits `maps/live.json` and finishes its reply; the play settings' `Stop` hook then runs the new `dmc redraw`, which draws the page again if `live.json` has changed since the last drawing. A fight always uses `live.json` (`CLAUDE.md` § Maps). `dmc redraw` also follows a map DMC drew by hand while `live.json` is unchanged: `dmc map` records, in `maps/live-source.txt`, the file it drew and that file's base place (path relative to `maps/`, resolved by the same `MapChecker.BasePath` as loading a map), so telling whether anything changed takes modification times, not a parse. If `live.json` is newer than the picture it is drawn even when the record names another file, and the record is rewritten. A page with no record follows `live.json` alone. If a `live.png` sits beside the page it is refreshed too. A refused file makes `dmc redraw` exit 2 with one line on stderr, which Claude Code gives to DMC to correct; the line says to fix it now and that a file still refused is reported again when the next reply ends. `stop_hook_active` true means Claude Code is already continuing, so the file is drawn if it is now fine but a refusal is not reported a second time: nothing is lost, because a refused file stays newer than the picture and the next turn's Stop hook finds it again. It prints nothing and exits 0 when no campaign is active, no page has been drawn, or nothing changed, and it reads stdin only when that is not a terminal. The hook command lets only exit 2 through, so an older `dmc` (unknown command, exit 1), a missing `bin/dmc` and a broken one stay silent. `CLAUDE.md` § Maps shrinks accordingly, and keeps one line: if a correction moves someone already narrated, tell the player. The remote player's picture, which a hook cannot send, stays a prompt rule in the `draw-map` skill: write the text, then `dmc map --png`, then send `live.png`; for a remote player the order depends on DMC alone, and the docs say so. Issue #6 stays open until a play test verifies all of this.
- **Reason:** The first fix, rewording § Maps to say the narration must be reply text written before the `dmc map` call, relied on the model doing something it had failed to do in all 6 map updates of the Phase 3 play test: Claude Code shows reply text after the tool calls that precede it in a turn, and DMC wrote no text before them. A rule the model already broke 6 times out of 6 is not a fix; a hook that runs after the reply is by construction later than the text. A new subcommand, and not an option such as `dmc map --pending`, because 0.1.2 treats an unknown option as a usage mistake with exit code 2, which a Stop hook turns into feedback that blocks the reply; an unknown command exits 1, which the hook command maps to 0. A modification-time comparison with `live-data.js` is the cheapest test of "changed" and needs no extra state beyond the record. Fights are pinned to `live.json` so that DMC never has to tell the hook which file a fight is in, and the hand-drawn case is covered by the record.
- **Costs and limits:** It needs release 0.1.3 and a pin before it does anything, and then only in sessions started with the play settings; elsewhere the map is not redrawn unless DMC runs `dmc map` itself after its reply text (the `draw-map` skill says so). It does not cover text maps or the remote player's picture. The first drawing of a map is still made by DMC with `dmc map`, before the narration. A file edited in the same clock tick as the last drawing is missed until its next edit. The Stop hook's behaviour (`stop_hook_active`, exit 2 as feedback) is taken from Claude Code's hooks reference, https://code.claude.com/docs/en/hooks; it was tested with a copy of the published `dmc` run by bash as the hook command, not inside a live Claude Code session.
- **Source:** Issue #6 and its Phase 3 comment (sessions `65b51f17` and `a4c01d59`, 2026-10-17); PR #37 and its two reviews.

## Feedback about DMC is recorded outside the campaign and tuned in one place

- **Date:** 2026-10-17
- **Decision:**
  - There are two kinds of feedback. Player options (how this player wants the game run) stay in `player-options.md`, as one-line preferences. DMC feedback (how DMC operates, such as a mistake, an inconsistency or too much context) goes to `feedback/` at the toolkit root. The test is `review-transcript`'s: would the same behaviour have been wrong for a different player with different preferences?
  - `feedback/` is git-ignored, keeping only `.gitkeep`, like `adventures/`, `modules/` and `rules/`, because entries quote the player and can contain spoilers. Turning an entry into a GitHub issue is a later step the worker takes with the user.
  - One file per entry, `feedback/YYYY-MM-DD-<slug>.md`, with a `status:` line in the frontmatter, and no index file. A repeat adds an occurrence to the existing entry and does not make a new file.
  - Nothing in `feedback/` is read during play except the titles `record-feedback` searches for a duplicate. Resume and full save never touch it.
  - If the player wants a change applied in this campaign now, DMC also writes one preference line in the campaign's `player-options.md`; the entry names it and the worker removes it once the fix ships.
  - No new `dmc` code. DMC has the date but no clock, so each entry records the real date, the story session and the player's exact words; a worker finds the moment with `dmc digest list --campaign <c> --after <date>` and a search of the `-turns.txt` file for the quote.
  - DMC records when the player gives feedback about DMC, corrects a DMC mistake that would be wrong for any player, or when its own slip forced a rewind or a rebuilt file. It never records the player's tastes there, and never edits the toolkit mid-game.
  - `review-feedback` is the only skill that tunes DMC: it reviews entries, finds the cause in the prompts, proposes changes and, on the user's word, files issues or makes PRs. `record-feedback` and `review-transcript` only produce entries, so `review-transcript` lost its Apply step. A toolkit test keeps `gh issue` and `gh pr` out of every other skill.
- **Reason:** Feedback had landed wherever DMC happened to be writing, in six places inside one campaign, several of them loaded at every resume, so a worker had to comb play files and the play files carried notes that were not about the game. One home per kind of feedback costs play nothing in context, keeps the entries understandable without the adventure, and shows by its occurrences how often a problem was raised. Keeping the tuning in one skill stops two skills proposing different fixes for the same cause.
- **Limits:** `Edit(feedback/**)` must be in `.claude/settings.json` for recording to raise no prompt in play. The existing scattered feedback in the first campaign is migrated by hand, with the player, after merge; that is local data and not part of the PR.

## Every resume starts a new session

- **Date:** 2026-10-18
- **Decision:** Every `/resume-campaign` ends the previous session and starts a new one, whatever brought it (a `/clear`, a new day, a compaction). Resume reads the previous log first, then closes it (fills an empty "Session end" block from `game-state.md`), creates the next `session-NNN.md`, and sets `Current session` to the new number only. If the most recent log has no scenes yet it is reused, so two resumes in a row do not leave an empty log. Scenes number from 1 in each session, and a citation is `sN` for a session or `sN.M` for a scene. Existing logs and `(s8)` citations are unchanged and keep their meaning.
- **Reason:** The toolkit never said what makes a session new, and a planned break always meant "keep using the current one", so one campaign's "session 8" grew to 38 scenes and 22 full saves over four days. A resume is the one moment DMC always passes through when context is reloaded, so tying the boundary to it needs no judgment, no asking and no counting, and keeps the log that the next resume reads short.
- **Limits:** A compaction in the middle of a scene also starts a new session, because the compaction hook runs the resume. The new log is then short and the scene continues in it. A session is therefore a stretch between resumes, not necessarily a sitting. Old logs are not split; the Silver Egg's session 8 stays as it is.
- **Source:** The user, 2026-10-18; `feedback/2026-10-17-session-boundary-undefined.md`.

## A fight is planned with an ending

- **Date:** 2026-10-18
- **Decision:** `CLAUDE.md` § Sizing fights gets a "How it ends" bullet: before initiative DMC knows how the fight ends and where the party can rest afterwards. An enemy fights to the end, flees for good, or can be caught within the fight. A creature that flees, heals, regenerates or calls for help needs a reason and an end DMC can state (where it goes, what it does there, when it stops); without one it does not do it. No enemy returns healed in the same fight, a call for help brings only what was counted, and one fight does not run into the next with no break. § Fun first now says "flee for good at half strength".
- **Reason:** In one campaign a troll fled at low HP, healed out of sight and returned, and called a second troll, so one fight ran thirteen rounds with no rest against enemies too big for level 2. The player's diagnosis was that this is a planning problem, not a chase problem: nothing made DMC plan how the fight ends and where the party can rest, and one enemy could pull in the whole dungeon. § Sizing fights already counted fights against rests across the adventure, but never asked how a single fight ends, and § Fun first listed fleeing as a tool with no limit. A narrow "no Dash chases" rule was rejected because several small decisions (a flee threshold, regeneration with a hiding place, a fast Dash, darkness, a reinforcement called by a roar) caused it.
- **Limits:** About three lines are added to `CLAUDE.md`, paid in every exchange. The rule relies on DMC planning before initiative; nothing checks it. It has not been tried in play.

## Resume and full save are bounded

- **Date:** 2026-10-18
- **Decision:** Every file that resume reads whole has a size to aim for, enforced at the full save, and the two procedures stop re-reading files they already hold. `game-state.md` under about 100 lines; `dm-notes.md` under about 150 lines with the notes about the player as lasting statements under about 40; each sheet under about 150 lines, with its history as the last section (`## History`) and old history moved to `character-sheets/<name>-history.md`. Resume reads a sheet down to its history. The full save's consistency check uses targeted Greps and short Reads instead of reading every changed file, the PC's sheet and every companion's sheet again, and archives canon with one Edit per file instead of one per line. All targets are in lines, after splitting long lines, because the files have lines of 1,000 characters and more.
- **Reason:** A review of twelve play sessions found that every resume added 104k to 165k tokens and that the full save was 8% to 34% of all context read. The causes were files that only grew (a 37,000-character PC sheet, 36,000 to 40,000 characters of DM notes, 29,000 of game state at the time), read whole at every resume, and a consistency check that read them all again. Only `canon.md` and the session log had a size rule or a partial read. Targets in lines, not characters, because there is no cheap way to count characters and a line count is already how `canon.md` is bounded.
- **Limits:** The targets are guesses; the first campaign's files are far over them and will shrink only as full saves trim them. A sheet that keeps its history in the middle is read whole until a full save moves it. Nothing enforces the targets except the skill telling DMC to count lines. A `dmc` command that reports file sizes would be more reliable and was not built. (It now is, and the targets are in tokens: see "Size rules are measured in tokens by `dmc size`".)
- **Source:** `feedback/2026-10-18-resume-costs-over-120k-tokens-in-a-mature-campaign.md` and `feedback/2026-10-18-full-save-is-the-largest-context-cost-after-the-resume.md`.

## How a skill is blocked in the play settings (Spec Kit, Phase 1)

- **Date:** 2026-10-21
- **Decision:** The play block for the Spec Kit skills (issue #51) is a deny rule per skill in the permissions of `.claude/play-settings.json`, written `Skill(speckit-specify)`, with the prefix form `Skill(speckit-*)` as the compact choice. It is a guard on what DMC itself invokes, not a promise about what the player can type. Skills that DMC must never reach by its own call also carry `disable-model-invocation: true`.
- **What the sources confirm:** The Claude Code changelog (https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md) says `Skill(name *)` permission rules work as a prefix match, like `Bash(ls *)` (2.1.139); that `Skill(name)` deny rules cover a nested skill listed as `<dir>:name` (2.1.260); and that `Skill(...)` denies match a skill's alias and display name (2.1.283). When Claude tries to invoke a `disable-model-invocation` skill it is refused and told to ask the player to run it (2.1.222), and such a skill still runs when the player types `/<skill>` (2.1.110). The `skillOverrides` setting has `off` (hidden from the model and from `/`), `user-invocable-only` (hidden from the model only) and `name-only` (description collapsed) (2.1.139 and later).
- **What it does not stop, or is not confirmed:** The documentation pages (https://code.claude.com/docs/en/permissions and https://code.claude.com/docs/en/skills) could not be fetched from the sandbox that wrote this entry, so these points are not confirmed from them: (1) whether a `Skill(...)` deny stops a command the player types; a user report (anthropics/claude-code#51386) says `deny: ["Skill"]` did not block a typed slash command, so assume it does not; (2) whether a denied skill still appears in the `/` list; only `skillOverrides: off` is documented as hiding it; (3) that `disable-model-invocation: true` keeps the description out of the model's context; the changelog says only that the model may not invoke the skill, and it was not confirmed that the description is dropped from the listing. Each must be checked in a live session (type the command; open `/context`) before the play block promises it.
- **Reason:** The block exists so that DMC does not wander into Spec Kit during play. A deny rule is the documented, checked-by-the-tool way to refuse DMC's own call; the player's typed commands are theirs to run and are not worth blocking. `skillOverrides: off` is the stronger option if the description cost or the `/` list matters, and is the fallback if the live check fails.
- **Limits:** The three unconfirmed points above. The rule syntax and the prefix wildcard rest on changelog entries, not on the reference page.
- **Source:** Issue #55, part of #51.

## A campaign export is a ZIP with a manifest of sizes and checksums (campaign export, issue #81)

- **Date:** 2026-10-22
- **Decision:** `dmc campaign export` writes a standard ZIP (`System.IO.Compression`, Deflate): `manifest.json` first, the campaign under `campaign/`, and the general `adventures/player-options.md` as `player-options.md` when there is one. The manifest (UTF-8 JSON, written and read through a source-generated `JsonSerializerContext`, `formatVersion` 1) lists every file's path, size and SHA-256 (lower-case hex), every empty folder, the module the campaign runs and the `dmc` version and UTC time of the export. Import checks size and SHA-256 of every byte it extracts, stops reading an entry at its declared size, and refuses an archive with an entry the manifest does not list or a listed file the archive lacks. Entries are stored as raw bytes with UTF-8 names; no line ending or encoding is ever changed. A reader accepts every `formatVersion` up to its own and refuses a higher one with "update dmc".
- **Reason:** ZIP is in the base class library, so no package is added and the Native AOT build is unchanged; it opens on every system without `dmc`, so the player can always reach their files by hand. A ZIP's own CRC-32 catches damage inside one entry but not a missing or extra entry or a manifest that disagrees, and cannot say which file is wrong; a per-file SHA-256 does all three and bounds a decompression bomb. Reflection-based `System.Text.Json` is not AOT safe and warnings are errors, so the manifest uses the source generator. Tar (no double-click opener on Windows), one JSON bundle (binary files such as `live.png` would need base64) and a copied folder (no integrity check, and easy to drop back inside `adventures/`, where DMC would search it) were rejected.
- **Limits:** The manifest is small but read whole (capped at 16 MB). Every campaign file is read into memory once; campaigns are a few MB. The export holds spoilers (`story/dm-notes.md`) and says so in `--help` and the user guide. A published module is never exported (copyrighted); import and `show` say when it is missing.
- **Source:** Issue #81; `specs/001-campaign-import-export/research.md` R2, R3, R4.

## Import is all or nothing through a staging folder inside `adventures/` (campaign export, issue #81)

- **Date:** 2026-10-22
- **Decision:** `dmc campaign import` checks the manifest and the list of entries first (nothing is created for a file that fails), refuses a name that already exists as a file or folder (also an empty folder, which a directory move would silently accept on Linux and macOS), extracts into `adventures/.dmc-import-<random>/`, verifying as it writes, and commits with renames on one volume: `player-options.md` into `adventures/` only if none exists (a move that never overwrites), then the campaign folder to `adventures/<name>`. If the folder move fails, the options file this run moved is moved back (or deleted if that fails) and the staging folder is deleted; if deleting fails, one line on stderr names it, as `dmc pdf` does. Import never writes `adventures/.active-campaign` and never changes an existing campaign or an existing general options file. The tests force the late failures with real obstacles (a file name of 300 characters that passes every check and that no file system can hold), so no test hook is in the binary.
- **Reason:** The same reasoning as `dmc pdf`'s staging folder: it is inside the destination so every step is a rename on one volume and a destination that cannot be written fails early, and a directory rename is atomic when the target does not exist, so a resumed session sees the whole campaign or none of it. The leading dot keeps the staging folder out of the campaign names the skills recognise. Extracting straight into `adventures/<name>/` would leave a half campaign that looks real after a crash; staging in the system temp folder may cross a volume and stop the move being atomic. Switching the active campaign behind the player's back could surprise a player in the middle of another campaign, so the last line of the output tells them to ask DMC to resume it.
- **Limits:** A killed process, or a file another program holds open, can leave the `.dmc-import-` folder behind; it is safe to delete. DMC's session start lists the folders of `adventures/` when no campaign is named, so a leftover could have been offered as a campaign; the review of PR #120 found this, and `CLAUDE.md` § Starting a session and the `resume-campaign` skill now list only folders whose names do not start with a dot (one clause each, issue #122). Extracted files all get the export's time as their modification time (the archive keeps no per-file times), so no file looks newer than another to the map redraw. A manifest may declare at most 100,000 files and 1 GB in all, which bounds what a crafted one can make import write. The options file and the folder are two renames, not one step; a crash between them leaves the new general options file and no campaign, which a second import completes (the options file is then kept).
- **Source:** Issue #81; `research.md` R5.

## Paths in an export are checked with Windows's rules on every system (campaign export, issue #81)

- **Date:** 2026-10-22
- **Decision:** Every path in an export is checked, at export and at import, before anything is written: relative, `/` separators only, no empty, `.` or `..` segment, no drive, none of `<>:"|?*` or a control character, no segment ending in a dot or a space, no `CON`, `PRN`, `AUX`, `NUL`, `COM1`-`COM9`, `LPT1`-`LPT9` (and `CONIN$`, `CONOUT$` and the superscript digits) (before the first dot, spaces ignored, any case), and no two paths equal when case is ignored (files and folders together, and no path that is both a file and the start of another path). Export refuses a campaign holding a symbolic link or junction (inside it, as the campaign folder itself, or as the general `player-options.md`), found with `FileSystemInfo.LinkTarget`, and a path import would refuse, so it never writes an archive its own import would refuse. A campaign name taken from the manifest must be one such segment that does not start with a dot; names with spaces and capitals survive. `--out` must be an existing folder or a file name ending in `.zip` (a typo such as `.zpi` is refused, not made into a folder).
- **Reason:** A crafted archive must not place a file outside the new folder ("zip slip"). Checking the Windows rules everywhere makes the promise that an export moves between systems true in both directions: an export made on Linux that Windows could not store is refused on Linux, with the same words. Sanitising names would silently break "byte for byte". A symbolic link would export a file from outside the campaign.
- **Limits:** `LinkTarget` is null for a Windows cloud placeholder (a file with the reparse-point attribute but no target), which is exported as the plain file it presents as. Path length is not limited by the checks; a name no file system can hold fails at the write, as one line, and leaves nothing.
- **Source:** Issue #81; `research.md` R6.

## Releases are immutable and their checksums signed; `dmc update` and an install line replace the pin (issue #67)

- **Date:** 2026-10-24
- **Decision:** Two measures are layered. (1) Releases are immutable once published, and published only after the maintainer approves: the publish job runs in the GitHub environment `release`, creates the release as a draft, attaches every file and then publishes it; every download is checked against the SHA-256 GitHub reports for it (`digest` in the releases API) and against the release's `SHA256SUMS.txt`. (2) `SHA256SUMS.txt` is signed with the project's private key, which exists only as the secret `DMC_RELEASE_SIGNING_KEY` of that environment; `dmc update` verifies the signature with two public keys built into `dmc` (the active key and a backup kept offline) and installs nothing otherwise. The signature is ECDSA P-256 over SHA-256, DER-encoded (`openssl dgst -sha256 -sign`), checked with `ECDsa.VerifyData`; .NET 10 has no built-in Ed25519, and a package for it is not worth adding. Nothing, no environment variable and no setting, can change the keys or skip a check in a release build (the test seam `DMC_UPDATE_TEST_ASSETS` changes where a release comes from, not what is checked). The first install is by an install line (`tools/install.ps1`, `tools/install.sh`, attached to every release) that checks the archive against the list and GitHub's digest but not the signature: it comes from the same release as everything it would check, and a `dmc` it downloaded cannot vouch for itself. The release workflow's dry run signs with a throwaway key made in the run, and `sign.sh` refuses to publish with a key that is not one of those built into `dmc`. Third-party actions in the release workflow are pinned to commit SHAs. A lost or exposed active key is recovered by signing the next release with the backup key and shipping a new key set (`.docs/releases.md`).
- **Reason:** The checksum pin in the repository (`tools/dmc-release.json`) was removed with `get-dmc`, so something else had to say which `dmc` players run. A corrupt download and a swapped release file are covered by both measures; a whole new bad release published with a stolen token or account is covered by the signature, as long as the private key, which only the approval-gated environment holds, is not taken too; an old release served as the latest is refused because `dmc update` only moves forward.
- **Alternatives:** A checksum pin on `main`, as before (weaker against a whole new release, since whoever can publish can usually merge, and it costs a pull request per release); keyless Sigstore signing or GitHub artifact attestations (no mature .NET verifier, and `gh` is not on players' machines); TUF (out of proportion for one program and one maintainer); Authenticode signing (declined 2026-10-17, see "Skip the Gatekeeper and SmartScreen checks"); HTTPS and a hash alone (a whole new bad release would be accepted).
- **Limits:** The install line's trust is HTTPS, immutable releases and two hash checks, like almost every scripted installer. If the API's limit for requests without sign-in is reached (60 an hour per address) the install line checks the list alone and says so. Immutable releases and the environment are repository settings only the maintainer can make (`.docs/releases.md`). Until the maintainer's keys are in `ReleaseKeys.cs` no release verifies.
- **Source:** Issue #67 and `specs/003-separate-player-install/` (research R8, R9 and R16; the user's decision of 2026-10-24).

## Size rules are measured in tokens by `dmc size`

- **Date:** 2026-11-10
- **Decision:** A new read-only command, `dmc size [NAME] [--check] [--folder PATH]`, lists the files `dmc-resume-campaign` step 2 reads, by that step's rules, with the estimated tokens (bytes ÷ 4) of the part read, the total, the largest sections and flags. Every size rule in the kit moves to it: the skills and templates no longer state a size in lines or words, and the numbers live in one place, `src/Dmc.Cli/Size/Budgets.cs`. The budgets: `game-state.md` 4k, `dm-notes.md` 10k (About this player 2k, Arc plan 1.5k), `summary.md` 3k, a PC's sheet 6k and any other sheet 4k (the part read); canon is read whole under 19k and archived down to 16k. The files the full save does not trim (the player options, the session log, the module files) have no budget. Any part read of 20k or 1,600 lines is flagged as near the Read cap. The resume runs `dmc size <campaign> --check` once, for its canon decision and a one-line warning near the cap; the full save's consistency check runs it and is complete only when it prints nothing or its report says why each line stays. `--check` prints nothing when all is well, and the command exits 0 whatever it flags.
- **Reason:** The third feedback review measured a resume of about 73k tokens, with `dm-notes.md` at 94k bytes cut short by the Read tool's cap. The only enforced limit was canon's 230 lines, set with no recorded reason, and a line ran from about 90 to about 307 characters, so lines measured the wrong thing; the files that grew had targets nothing checked, and the review found every rule against the growth already existed. A number a tool prints is harder to wave through. Bytes ÷ 4 is the review's method and needs no tokenizer; it undercounts (a 23.5k file was cut), so the near-cap mark is 80% of the cap. The canon limit is set for consistency, not to save tokens: canon is nearly all live facts and a searched canon depends on DMC searching, so the long campaign's canon (15.5k, about 17k once fight stories reach it) stays read whole. 16k keeps the old ratio of 200 to 230. The budgets are the review's starting points, to be tuned against `review-transcript`'s slip counts; a PC's sheet is 6k because a healthy one measured 5.4k, and a flag that cannot be fixed is noise. The summary's 3k is looser than the old "600 words" (about 1k), which no campaign met. Exit 0 with flags, because DMC acts on the output and a non-zero exit shows as a tool error.
- **Limits:** The estimate is an estimate. The flags match the markers the templates write (a Last played line, an alive / started count of 0, DONE or RESOLVED, section names), so an older campaign with other section names is flagged less; issue #172's migrations bring it to the standard. Which sheets the resume reads is matched by name, so a Present line that names someone off scene counts their sheet too, which overstates the read. Measuring does not shrink a file: the full save does.
- **Source:** Issue #174; `specs/006-dmc-size/` (research R1 to R11); `feedback/2026-11-08-campaign-files-outgrow-resume-and-slips-rise-late-in-a-campaign.md`; the PR #173 review.
- **Amended 2026-11-15** (issue #179, Phase D, spec 013): the reason above kept the long campaign's canon read whole for consistency. Phase D reverses it, on the user's word that the gate is checked after release: canon at 6,000 tokens or more is read as its always-read sections and the scene's best matches, and the 19,000 limit is now only where the full save archives. See "Canon is read as Rulings, Prices and the scene's best matches". Reversed 2026-11-15 by the gate's canon rollback: canon is read whole under 19,000 again (that entry's amendment).
- **Amended 2026-11-24** (issue #246, spec 021): the estimate is no longer bytes ÷ 4, which undercounted by about 1.6 times: `dmc size` said the long campaign's resume read 57k, and two resumes grew the context by 109k and 112k. Every token figure now comes from `Measurement.Tokens`, 2 tokens for 5 characters of text (0.4 a character; a CR before an LF and a byte-order mark are not counted), and a Read call costs that and 160 more. The rate was fitted on 611 batches of Read calls in 194 Claude Code logs (median error 2.1% on batches of 10,000 characters or more, out of sample), and checked against real counts of four campaign files taken from Claude Code's own usage figures (−7% to +5%, the same on Sonnet and Opus); Read's line numbers cost close to nothing. Each budget, limit and threshold is 1.6 times its old number (`game-state.md` 6,400, `dm-notes.md` 16,000, a PC's sheet 9,600, a play card 1,600, canon read whole below and archived above 30,400 and down to 25,600, and so on: the table in [campaign-files.md](campaign-files.md)), so it allows the same text, and no file is newly over one. The budgets keep their text and not their numbers because the same numbers in real tokens would make every full save trim about 40% more, and the full save rewriting lines to fit is the probable source of the false sheet lines of issue #262. The near-cap mark is now 18,000 tokens of Read cost: the old 20,000 was about 32,000 real tokens, past the Read tool's cap of about 25,000, so the warning came after the cut; 18,000 flags every part of 20,000 real tokens. Canon within its limit is not flagged near the cap: its limit is past the cap (as it already was in real tokens), the resume reads it in two reads when the Read tool says it is too large, and a flag would send the full save to trim it. The report's total is what the resume pays to read the files, about 95k for the long campaign. No migration is needed: no template, shape or allowed text changes, and on 24 campaigns the new `dmc size` printed no budget or canon flag the old one did not. **Limits:** it is an estimate, about 8% off on small reads; a file within about 1% of a budget can fall just under it, since CR line ends and non-ASCII characters counted as bytes before (it is trimmed less, never more); it must be measured again if a model's tokenizer changes (the scripts are with the slip analysis's evidence); the Read cap was not re-measured, since no log holds a refusal; and module files and sequel digests written to the old mark (The Crooked Moon's monster and item files and several chapters, The Silver Egg's digest `people` files in Rorn's Landing) are now reported by `dmc module check` and `dmc campaign sequel --check`, which run only at ingest and at a sequel import. See `specs/021-real-tokens-dmc-size/research.md`.

## Campaign files are brought up to a new standard by migrations DMC follows and `dmc` verifies (issue #172)

- **Date:** 2026-11-10
- **Decision:** A change to what campaign files should hold ships a migration: a numbered Markdown file in `kit/migrations/` (installed to `migrations/`) that DMC follows in a play session, through a new skill, `dmc-migrate-campaign`. `dmc campaign` gains the steps that must be exact: `standard` (where a campaign stands), `backups` and `backup` (a checked backup, the removal question, pruning on the player's yes), `verify` (the proof that no content was lost) and `restore` (the way back). The parts, each with its reason:
  - **The standard is an integer in `adventures/<campaign>/.standard`** (research R2), 1 when the file is missing. It travels with export and import, costs no context, and only a passing `verify` (or `standard --init` for a new campaign) writes it, so DMC cannot mark a campaign current by hand. A line in `game-state.md` or `player-options.md` would be read every resume and edited by the player and by the migration itself.
  - **Migrations are numbered on their own**, not by release (R3): a release may carry none or several, and two PRs that both add one conflict on the file name. The kit's standard is the highest number. The shipped cases are 002 (history is a sheet's last section, PR #68), 003 (the Names they use line, PR #170) and 004 (the third feedback review's lean notes, PR #173). A campaign created after those PRs has no `.standard` and runs them over files already current, so every step checks whether it is needed.
  - **Verification accounts for every unit of old content** (R5): each non-blank line of the backup, normalised (whitespace, list markers and heading marks; table rules and comments skipped), must be found in the migrated campaign, or contained in a longer line when it is 20 characters or more, or be listed in an accounting file as reworded (with an anchor that is in the campaign) or dropped under a class the pending migrations declared and the player was shown. Headings are units, because in campaign files they carry names. A file left unmigrated fails it. `backups/` and `.standard` are never compared, so an anchor cannot match itself. `verify --list` gives DMC the ids it cannot compute. A diff reports a reorganised file as all changed, and a model's own "nothing is missing" is the failure the feature exists to prevent.
  - **Every migration names a shape check** (R7), a small function in `MigrationChecks`, so a file left in the old shape fails even if DMC writes no `skipped` line. Finished fights and closed threads move verbatim to `story/dm-notes-archive.md`, as the current standard does, so they are matched, not dropped.
  - **Sizes are left to `dmc size`** (R6). A migration holds no size target, and `verify` reports none; after a pass the skill runs `dmc size NAME --check` and relays each line as work for the next full save. Spec 006 merged first, so this PR adds that step. A migration cannot shrink a file below the live material it holds without breaking verification, so a size over budget is never a failure.
  - **Backups are pruned after the write, on a flag, and a mark records an unfinished migration** (R8). `backups` prints the removal question with the flag a yes allows, `backup --prune` applies it, and the skill holds none of the numbers, so the retention rule lives in `BackupFolder` alone. Pruning after the write keeps the last good backup when the disk is full. `backup` writes `<file>.migrating` when a migration is pending (on a current campaign `verify` has nothing to verify, so the mark could never be cleared), and a passing `verify` removes every mark of the campaign; while it exists `standard` says `unfinished`, `backup` refuses, and `verify` and `restore` default to that backup, so a rerun never backs up half-migrated files. Comparing standards instead of writing a mark would pick the wrong backup after a restore and more play.
  - **Restore is its own verb, a plan by default** (R9), so `import` keeps refusing to change an existing campaign. The confirmation DMC relays from the player is the `--yes` flag. Its warning compares the campaign with the record a passing `verify` wrote, so it names play after the migration, not the migration's own changes. Renames on one volume keep the campaign whole if the restore fails, and a later run recovers an interrupted one.
  - **Recovery from an interrupted restore never deletes what it cannot place** (amendment A12, from the PR's code review). A restore's staging and aside folders share an id, so the folders left say how far it got. The campaign set aside is deleted only when its staging is gone (the rename into place was done), a staging is deleted only once the `backups/` moved into it is back, and every migration verb recovers first, so a campaign never reads as current while its mark sits in a staging folder. When a new campaign folder appeared after the rename aside, nothing is touched and the player chooses which to keep.
  - **Backups are ordered by the UTC time in their manifests** (A12), not the local time in their names, which runs back an hour once a year. The names stay local, as the spec asks, because the player reads them.
  - **`migrations/` is protected by `Edit(/migrations/**)` alone, and the kit's `Write(...)` deny rules go** (A13). Claude Code applies an `Edit(...)` rule to every tool that edits files, `Write` included, and warns that a `Write(...)` rule is never matched. The rules for `/CLAUDE.md`, `/.claude/**`, `/templates/**` and `/.dmc/**` lose nothing, and a toolkit test refuses a `Write(...)` rule so none comes back.
  - **CI proves each migration on a golden fixture; a model run is the author's** (R11). `tests/Dmc.Tests/Fixtures/migrations/NNN/` holds `before/`, `after/` and the accounting; the golden test backs up `before/` with the real command, replaces it with `after/`, and requires `verify` to pass, and to fail with a line removed, an undeclared drop class claimed, or the touched files left as they were. CI cannot run DMC, so the author runs the migration live once and reports it in the PR.
  - **Import reports a campaign that is not current** (R12). An export made before this change can hold the campaign's `backups/` folder; import (and restore) leaves it out and says so rather than refusing the file (A12), so such an export stays importable. Refresh and update say once when campaigns are behind, after a refresh that changed files (a refresh that changed nothing stays silent). Resume runs `dmc campaign standard` and says one line only when it is not `current`; on `unfinished` play waits until the migration is finished or restored.
  - **The catch-up clauses leave the skills** (FR-017): "add the line if an older sheet lacks it" (sheet update) and "move it there if it is not" (full save) are now migrations 003 and 002, and a toolkit test refuses such wording.
- **Reason:** Issue #172: the third feedback review changed what `dm-notes.md` and `game-state.md` hold, and a running campaign only reaches the new shape piecemeal, at full saves, with no order and no check. The long campaign's resume read about 73k tokens. The work needs judgment (which fights are finished, which orders are in play, how a fight becomes a Timeline line), which only DMC can do, so `dmc` does everything that can be exact and testable.
- **Cost in play** (Constitution II, measured as bytes ÷ 4, the method of `dmc size`): the new skill's description is 255 bytes, about 64 tokens, in every session's list of skills. The resume skill grows by about 140 tokens, read once per resume, plus one `dmc campaign standard` call whose output is `current` (8 bytes) on a current campaign. The two catch-up clauses removed save about 33 tokens where those skills load. The migrations (2.2k, 2.2k and 8.9k bytes) and the skill body (4.5k bytes) load only while migrating.
- **Limits:** Verification proves nothing was lost verbatim or by a stated mapping; it cannot prove a rewording kept its meaning, and a short fact merged into an unrelated long line can pass as contained (the 20-character floor and the player-shown drop list keep that rare). The golden fixtures prove the declared drops, the checks and the accounting agree with a correct result, not that a model following the prose produces it. A hand-edited Opposition table that no longer matches the template fails `no-dead-opposition-rows` as "no table found", which is FR-010's behaviour, not a pass.
- **Source:** Issue #172; `specs/005-campaign-migrations/` (research R1 to R13, amendments A1 to A13); the PR #173 review and the code review of PR #176; `feedback/2026-11-08-campaign-files-outgrow-resume-and-slips-rise-late-in-a-campaign.md`.

## Image prompts state facts only; a missing detail is asked for, never assumed (issue #178)

- **Date:** 2026-11-10
- **Decision:** `dmc-generate-image-prompt` builds a prompt's content only from the campaign files: everyone present in a wide shot unless the request says otherwise, each figure's species as the files give it, size as a comparison with someone in the picture (where the files give none, by the figures' size categories in the campaign's rules: the same size drawn the same, a smaller one smaller and a larger one bigger, with no bare category or height in the prompt, since D&D gives most creatures a size category rather than a height; the user's ruling on PR #186's review), a creature named by its kind, and nothing the character has not perceived, by the DM rules' "Say only what the listener could know", which the skill points at and does not restate. A visual detail no file holds is left out and named after the prompt; what the player then says is written to the sheet's Appearance line, or to the "Distinguishing trait or voice" cell of a minor NPC's row. Content decides who is shown and how wide the shot is; a style decides only the look, and wins nowhere it touches content. The session log keeps out what the player says out of character (`templates/session-log.md`), so the prompt is not logged.

## Retrieval runs over the markdown, with no stored index (issue #179)

- **Date:** 2026-11-10
- **Decision:** `dmc lookup` and `dmc recall` read the markdown files on every call and build what they need in memory: no vector database, no graph database, no SQLite store and no index on disk. The markdown stays the source of truth, and play never depends on `dmc`: when it fails, DMC searches and reads the files as before.
- **Reason:** The slips that hurt are exact facts (a name, a price, a ruling), which keyword search finds and embeddings blur; an embedding model would need a network or a large model inside a Native AOT binary. The measured corpus (a sequel, its predecessor and a module, a few megabytes) parses and indexes in well under a second, so an index built on the fly cannot go stale, and hand-editing, export, backup, migration and verify keep working on plain files.
- **Limits:** A paraphrase that shares no word with the line it means is missed; the fallback covers it, and embeddings are revisited only if `review-transcript` shows such misses that a second search does not fix.
- **Source:** Issue #179 (its decision table and evidence); `specs/009-retrieval-lookup-recall/`.
- **Partly superseded 2026-11-17** by "`dmc` is a required part of DMC (issue #208)": the clause "play never depends on `dmc`: when it fails, DMC searches and reads the files as before", and the fallback in Limits where it meant a failing `dmc`, no longer hold; a missing `dmc` stops play. A recall or lookup that finds nothing is still followed by a search, and the markdown stays the source of truth.

## Recall ranks by keyword relevance weighted by authority (issue #179)

- **Date:** 2026-11-10
- **Decision:** `dmc recall` ranks line units by BM25 (k1 1.4, b 0.6, the issue prototype's settings, its common words and its suffix stripper, with two changes: a letter of any script counts, and apostrophes at a word's ends are dropped, PR #187's code review) times a weight per file: canon 1.30, archives and history 1.20, sheets 1.15, other campaign files 1.05, session logs 1.00, a module 0.80, and × 0.95 per step back the Predecessor chain. It searches the campaign, its Predecessor chain and each of their modules, ranked below every campaign file; a hit is one line, trimmed to 700 characters around the match, within 6,000 bytes in all.
- **Reason:** In the issue's recall test, plain BM25 over lines put the answer in the capped output for 28 of 30 named and 22 of 30 indirect questions, and curated lines (canon, archives, sheets) proved more reliable than narrative. A moderate weight lets canon win where the match is about equal without hiding a much better session-log line (a tie-break alone would never lift canon; hard tiers would bury the best match). A predecessor's module is reached because recall already reads the predecessor's options and a printed name or number only that module holds would otherwise be out of reach (the user's answer in `/speckit-clarify`). Neighbouring lines are not shown: they would halve the hits that fit.
- **Limits:** The weights are starting values. The recall test is rerun on the maintainer's play folder after migration 004 (`tools/recall-test.ps1`), and a follow-up tunes the weights or the trim if the figures fall. The stemmer misses some pairs ("horse" and "horses").
- **Source:** Issue #179; `specs/009-retrieval-lookup-recall/research.md` R1 to R6.

## Lookup matches headings exactly, and never prints text cut from a PDF (issue #179)

- **Date:** 2026-11-10
- **Decision:** `dmc lookup` matches a heading by its normalised text (case, emphasis, punctuation and a trailing page reference ignored), then by all of the request's words; several matches print a list, never a guess. A rules reference kept as a PDF gives the matching rows of `rules/index.md`, or the PDF pages whose extracted text holds the words, as numbers only.
- **Reason:** A near miss that printed the wrong stat block would be a wrong number stated as fact. Extracted PDF text drops digits from tables (the issue's module), and an entry's end is a guess in plain text, so lookup points at the pages and DMC reads them as before (the user's answer in `/speckit-clarify`; the page numbers are the plan's addition, since the index names no single entry).
- **Limits:** A heading phrased differently from the request ("Goblin Chief" for "Goblin Boss") is not found; the failure names the nearest headings.
- **Source:** Issue #179; `specs/009-retrieval-lookup-recall/research.md` R7 to R9.

## A closed campaign is closed for good (issue #180)

- **Date:** 2026-11-11
- **Decision:** A finished campaign can be closed, only on the player's word, by a new skill, `dmc-close-campaign`, and one verb, `dmc campaign close NAME [--yes]`. Closing is a last full save with these differences: no sheet history moves out; canon archives nothing and gains the loose ends and each fact's reason and means; every secret is gathered back into `dm-notes.md` with its outcome, `revealed sN`, `never revealed` or `abandoned`; `summary.md` § How it ended replaces § Where things stand; nothing is trimmed for size; and the stamp adds no planned break. Then the closing backup `backups/<campaign>_closed_<stamp>.zip`, holding the mark from memory, and a byte copy in `exports/`, each checked, and last the mark `adventures/<campaign>/.closed` (the UTC time and the closing backup's name), with a rollback of what the run wrote on any failure. The mark goes last (PR #190's review) so that a close stopped part-way, by Ctrl+C or a crash, which no rollback can catch, leaves the campaign open rather than closed with no backup; a stray closing backup it may leave is never counted. Nothing reopens a closed campaign: a sequel continues its story. Every `dmc` writer refuses it in one line (`backup`, `restore`, `standard --init`, `map`, `pdf` and `digest show` output into it); `redraw` does nothing; `verify` compares its bytes with the closing backup and writes nothing; resume stops at `closed`; `kit/dm-rules.md` § Accuracy says never to change it; the kit's settings deny edits to the mark. DMC may suggest closing at two moments only, when the main story ends and when the last open thread closes.
- **Reason:** The user's decisions in the spec's clarifications: closed forever, sequels only; a full save and a backup; a new skill, so the full save gains no closing text and play pays only its description; the records in the files that already hold their kind; secrets gathered back so a sequel's digest finds them in one place. A fact a program must trust lives in a file only `dmc` writes (as `.standard`); the mark goes before the backup so the backup holds the campaign as closed and an import of it is closed too; the closing backup's name is outside the counted backups' pattern, so no prune can remove it; the name is fixed once and a clash refuses the close rather than choosing another name (the user, 2026-11-11). The standing cost of an ordinary session is the skill's description, one clause in resume and one in `dm-rules.md`: 383 bytes, about 96 tokens, measured as bytes ÷ 4, under SC-006's 100; an ordinary full save gains nothing.
- **Rejected:** A PreToolUse hook refusing any edit under a closed campaign would make the freeze exact, but it starts a `dmc` process on every Edit and Write of every play session for a state entered once per campaign, and `verify` already reports a broken freeze. Revisit if a feedback review ever finds a closed campaign edited in play. Separate verbs for the backup and the mark were rejected because the order and the rollback would then be the skill's; writing the mark last because the closing backup would not hold it.
- **Limits:** DMC's own edits of a closed campaign's other files are stopped by the rule in `dm-rules.md`, not by a deny rule; a hand edit outside play is not stopped, and `verify` finds it. Verifying against any other export (a backup against the live campaign, an import against its file without `--backup`) is issue #189.
- **Source:** Issue #180; `specs/010-campaign-close/` (spec § Clarifications, research R1 to R11).

## Campaigns link through a Continuity section, followed both ways (issue #179, Phase B)

- **Date:** 2026-11-11
- **Decision:** A campaign's links live in a `## Continuity` section of its `player-options.md`: Continues (one closed campaign a sequel carries on), Side campaign of (one main campaign), Shares a world with (any number). `dmc` follows links both ways, breadth first, each campaign once, into a linked set with distances and four labels, `continues`, `sequel`, `side` and `world`; the set has one home, `Campaign/CampaignLinks`. Migration 005 moves the old Predecessor line there, and a file with no section is still read through that line, so a closed campaign, which is never migrated, keeps its link. The resume hears only of problems in the lines of campaigns that are not closed.
- **Reason:** A side campaign or a one-shot in the same world was invisible to the main campaign. Links one way would make the player write each link twice and keep them in step; four labels are all the play rule needs (only a `continues` fact can be known to characters who were there, and a `sequel` fact, seen from a predecessor kept open, has not happened yet). The links are the player's intent, not a fact a program must trust, so they live in a file the player reads and edits; whether a linked campaign is closed is read from that campaign's own mark. A closed campaign's file can no longer be changed, so a problem in it would be repeated at every resume with nothing the player could do; recall and `dmc campaign links` still name it.
- **Rejected:** A `links.md` file (one more file per campaign for three lines); a dot file like `.closed` (links are the player's to edit); folding link notices into `dmc campaign standard` (its output is a state skills branch on); a `--check` form of `dmc campaign links` at every resume (a command call each session, against spec 011's 150-token cap): the notices come through the `dmc size --check` the resume already runs.
- **Source:** Issue #179; `specs/011-linked-campaigns/` (research R1 to R3, the analyze session's clarifications).

## Recall ranks a digest above the folder it digests, and prints a line once (issue #179, Phase B)

- **Date:** 2026-11-11
- **Decision:** `dmc recall` searches the whole linked set, the digests (`digests/<campaign>/`) any campaign of it holds and each module once. A digest's lines take the archive's weight, 1.20, times 0.95 a step to the campaign it digests; every file of a campaign whose digest a campaign nearer the start holds is the last resort, × 0.85. For a sequel holding its predecessor's digest: the sequel's canon 1.30, the digest's copy 1.14, the predecessor's own canon 1.05. Lines whose normalised text (the migrations' rule) is the same are merged before ranking into the best-weighted copy, DM-only when any copy is. A hit from another campaign carries its label after its name; a digest's hit carries the digested campaign's label after its file, so it is not read as the holder's.
- **Reason:** A digest copies lines word for word, so without these rules a recall prints the copy and its source one after the other and halves its useful hits within the cap; the digest is only worth writing if recall finds it first. Merging before ranking, not when printing, keeps the copies in later sequels' digests from lowering the weight of their own words, and keeps a DM-only source's mark on its copy. The archive's weight places the digest where its lines came from, curated facts resume does not read, and below the sequel's own canon, so an older fact never outranks the sequel's newer one about the same subject. The last-resort factor keeps the old folder searchable, with its session logs' full text, rather than dropping it.
- **Rejected:** Leaving a digested campaign's folder out of scope (loses the last resort); a digest weight above canon (the opposite of "canon wins"); a label in front of a digest's file (it reads as the holder's link); skipping a duplicate only when printing (the first version: the PR's code review found the copies still lowered their words' weight).
- **Source:** Issue #179; `specs/011-linked-campaigns/research.md` R4 to R6.

## A migration may ask before its backup (issue #179, Phase B)

- **Date:** 2026-11-11
- **Decision:** A migration file may have an optional `## Before the backup` section between What changes and Steps, which `dmc-migrate-campaign` follows after the player's yes and before the backup. Migration 005 uses it to ask, when a sequel's predecessor is still open, whether to close it (closing is permanent), and on no whether the player is sure; a second no stops with `Migration stopped until the previous campaign is closed. You can close it by running: /dmc-close-campaign <predecessor>`. On yes the close skill closes the predecessor by name: the full save takes a campaign its caller names, so the active campaign never changes.
- **Reason:** The user's answers in spec 011's clarifications. Asked before the backup, a stop changes nothing: the campaign stays `behind` and playable, and the migration is offered again at the next resume; asked in Steps, a stop would leave it `unfinished`, which blocks play. A section in the migration keeps this migration's question in its own file, and the skill's change is one generic sentence. Naming the campaign, rather than switching `.active-campaign` and back, means an interruption mid-close leaves the sequel active.
- **Rejected:** The check written into the migrate skill by name (one migration's logic in a generic skill for ever); writing the link without asking (two open campaigns telling one story that can disagree).
- **Source:** Issue #179; `specs/011-linked-campaigns/` (spec FR-028a, research R13).

## A sequel's import is proved against the closing backup (issue #179, Phase B)

- **Date:** 2026-11-12
- **Decision:** `dmc campaign sequel --list` and `--check` read the closed campaign's lines from its closing backup, the ZIP its `.closed` mark names, never from the live folder; every form also refuses a closed campaign that differs from that backup. The lines that count are every line of canon, the canon archive, `module-progress.md` and every file in `character-sheets/`, with § Secrets of the DM notes and § How it ended of the summary.
- **Reason:** The closing backup is the record that a closed campaign cannot change; checking it means a hand edit to the closed folder after closing can never pass as accounted. Every line of every sheet counts, so a returning character's appearance, voice and names, and a sheet's own secrets, are proved too, not only their history. DM plans and game state are left out: the brief carries what still matters of them, and accounting each would cost thousands of lines for nothing a sequel asks.
- **Rejected:** Accounting every line of every file; accounting only a sheet's history (the first plan).

## A digest's accounting says `merged` (issue #179, Phase B)

- **Date:** 2026-11-12
- **Decision:** A digest's `accounting.tsv` has the shape of a migration's accounting file and the same reader, `AccountingFile`, which now takes the word for a line kept in changed form: `reworded` in a migration's file, `merged` in a digest's, each refusing the other, with the same 8-character anchor rule. A digest's file has no `skipped` lines, and its drop classes are fixed: `superseded`, `not-canon`, `structure`, `bookkeeping` and `stat-block`.
- **Reason:** A digest merges lines that say the same thing into one under a subject; it does not reword them. One parser keeps the two files from drifting apart, and the word tells a reader which kind of file they are in.
- **Rejected:** A second parser for digests; `reworded` in both.
- **Source:** Issue #179; `specs/011-linked-campaigns/` (research R9).

## The sample test draws 20 facts and 5 people from a seed in the closing backup (issue #179, Phase B)

- **Date:** 2026-11-12
- **Decision:** `dmc campaign sequel --sample [--round N]` seeds SplitMix64, written out in `dmc`, with the first 8 bytes of the closing backup's SHA-256 plus the round. It draws 20 fact lines from the digest's subject files, split between copied lines and session-only lines in proportion with at least one of each, and 5 people from the closing backup's sheets and minor NPCs, at least one carried. One fresh subagent answers from the digest alone, DMC compares with the closed campaign, and the sample passes with no miss; a redraw after a fix is the next round.
- **Reason:** The same backup and round always draw the same items, on any machine and runtime (`System.Random` may change), so a pass can be checked again. Facts come from the digest so session-only facts are tested, which the sources do not hold; people come from the closed campaign so a person the digest lost can be drawn. The accounting, not the sample, proves no line was lost; 25 items is enough to catch a digest that scattered or garbled its subjects at a cost a long import can bear.
- **Rejected:** A random seed recorded in a file (not reproducible from the backup alone); facts drawn from the sources or the session logs; people drawn from the digest's headings.
- **Source:** Issue #179; `specs/011-linked-campaigns/` (spec FR-024, research R11).

## Each part of a sequel's import reads only the subjects it adds to, and keeps its files under the cap (issue #179, Phase B)

- **Date:** 2026-11-12
- **Decision:** In `dmc-new-campaign` § 1c, a part's subagent finds a subject an earlier part wrote with `dmc lookup <folder> <heading>` or a search of the digest and reads only that section, never a whole digest file. Before it ends it runs `dmc campaign sequel <folder> --check` and, for each `too large:` line, moves whole subjects into the kind's next part (`people-2.md`, then `people-3.md`) and checks again.
- **Reason:** In the Phase 9 rehearsal, The Silver Egg's digest built into a copy of Rorn's Landing, each subagent was told to read "what earlier parts wrote" and read the whole growing digest, so each part was slower than the last. One judged a 36k-token `people.md` to be "about 20k", nearly twice the cap. With both rules, the full run passed `--check` (1,510 units; 16 files, the largest 19.6k tokens) and the sample's first round.
- **Limits:** The import is still slow: 59 minutes and 41.4M tokens for the digest alone, because the model retypes every line it copies. The fix for that changes `dmc` and is proposed in issue #198.
- **Source:** Issue #179; spec 011 Phase 9 (T076/T077); issue #198.

## Recall ranks a digest's scene spine at the weight of the logs it copies (issue #179, Phase B)

- **Date:** 2026-11-14
- **Decision:** `dmc recall` ranks a digest's `spine.md` at 1.00 × 0.85 times the digest's distance factor. That is what a line of the digested campaign's own session log weighs as the last resort, not the 1.20 of the digest's other files. A digest folder counts as held only once it has a `.md` file other than `index.md` and `spine.md`, the two files `--start` writes. `SequelDigest.IsFactFile` is the one rule for this, and the accounting and the linked set both use it.
- **Reason:**
  - **The shortfall.** Phase 9's recall test on the maintainer's play folder (T077) gave 27 of 30 named answers, against the 28 that SC-004 asks for. The Silver Egg was digested into Rorn's Landing.
  - **Why.** The spine's scene lines are short and name places such as "the Birch shop" in almost every line. At the digest's 1.14 they filled 8 of the 20 hits for "How long is the Birch shop's lease?", and the answer was pushed out.
  - **Why the spine stays searched.** It is the only place recall finds a scene's title: heading lines are never units, so a session log's `### Scene M:` titles are not searched. It is also the only one when the digested campaign's folder is not on the machine.
  - **The figures.** On the play folder: 28 of 30 named and 23 of 30 indirect at 0.81 or 0.67; 27 and 23 at 0.95 and at 1.14. Leaving the spine out also gave 28 and 23.
  - **Why the held rule changed.** A folder holding only the index and the spine had already made the digested campaign the last resort, and stopped its legacy being named, though no line had been copied yet. A real import is about an hour of parts.
- **Rejected:**
  - Leaving the spine out of recall. This was the first version of PR #203, and its code review found it would leave scene titles unrecallable.
  - Leaving the weight as it was. One question is the whole margin SC-004 allows.
  - Tuning BM25's length normalisation for every file. It changes every campaign's ranking and needs its own spec.
- **Limits:**
  - The margin is narrow. At 0.95 the test misses the lease again.
  - SC-004's second clause misses one fact. For Tallow's "It isn't a vote", a different line from The Silver Egg's logs ranks above the digest's long merged line, which falls out of the output. In 4 more of the 44 answers a folder line ranks above the digest's, but the digest's line is printed too. Long lines score lower under BM25's length normalisation. Tuning that changes every campaign's ranking, so it is left for later.
- **Source:** Issue #179; `specs/011-linked-campaigns/` (research R4, T103, T077); the code review of PR #203.

## A sequel's import keeps its parts on Sonnet (issue #198)

- **Date:** 2026-11-14
- **Decision:** `dmc-new-campaign` § 1c is unchanged: the parts of a sequel's import run on the model the DM runs on, not on Haiku.
- **Reason:** The Phase 9 import was rerun in a copy of Rorn's Landing with the DM on Sonnet at high effort and the 11 parts on Haiku at high effort.
  - **Quality matched.** `dmc campaign sequel --check` passed after one fix round (one unaccounted line, one missing anchor): 1,509 units, 1,305 copied, 41 merged, 163 dropped, against Sonnet's 1,343, 9 and 157. ## Legacy files are a running list ordered by session numbers (issue #179, Phase B)

- **Date:** 2026-11-13
- **Decision:** A campaign linked to an open campaign keeps `legacy.md`: what changed in the shared world, one line per change with its `sN.M`, stamped `- **Written**: session N, yyyy-MM-dd`. A reader records what it folded on its `game-state.md` line `- **Legacies folded**: side-quest s14`; `dmc size --check` names a legacy written in a later session than the one recorded, and tells the writer at every full save, with `legacy due:`, which lines to drop, in words the model acts on: `drop the lines from session N and earlier`, N being the lowest session the open readers record, or `keep every line the budget allows` while any records none. Past the 3,000 budget the oldest lines go. The closing save acts on these lines too. A legacy is not named when this campaign, or one nearer it in the set, holds that campaign's digest.
- **Reason:** Session numbers are the one order DMC always writes; dates have no times (Rorn's Landing's last full save line is `2026-11-11, session 47, through scene 2`), and file times change with exports and copies. A rewrite at each save would lose the first of two saves made before a reader resumes, and the writer cannot see what each reader folded, so `dmc`, which already reads the linked set, names what to keep. `legacy due:` prints at every check, not only when the stamp is behind the current session, because resume can reuse a session log with no scenes and two saves can fall in one session. The full save folds what a `legacy:` line names rather than what it remembers reading, which a compaction can lose. A digest already carries everything its campaign's legacy says, so naming that legacy as well would only fold the same facts twice. Two campaigns played at once in two terminals are not supported: the player runs one adventure in one terminal.
- **Rejected:** Dates or file times; a record file per pair of campaigns; holding every line until every reader folds it (the file would grow without bound; a reader left unplayed misses only the oldest lines, which the writer's canon still holds for recall); a scene in the stamp for two sessions at once (out of scope).
- **Source:** Issue #179; `specs/011-linked-campaigns/` (research R12, the analyze sessions of 2026-11-11 and 2026-11-13).

## A legacy never flows back against the story (issue #202)

- **Date:** 2026-11-14
- **Decision:** A campaign comes after another's story when its chain of Continues lines (or old Predecessor lines) leads back to the other or a campaign played alongside the other, however else it is linked, or when it is reached only through such a campaign. That is a sequel and what lies beyond it, and, for a side campaign, the sequel of the campaign it is played alongside. `dmc size --check` never prints a `legacy:` line from a campaign that comes after this one's story, and never counts a campaign this one comes after as a reader on this one's `legacy due:` line. Side and shared-world campaigns played alongside flow both ways, and the close goes on folding their legacies as T099 has it.
- **Reason:**
  - **The bug.** In spec 011 Phase 9, The Silver Egg was finished but not yet closed, so Rorn's Landing, its sequel, wrote a legacy for it. Closing The Silver Egg folded that legacy into its canon, under "After the story". The sequel's import copies the closed canon, so Rorn's Landing's own events would have come back into its digest as The Silver Egg's. This time the import dropped them by hand.
  - **Why that is the line.** A sequel's world changes come after the earlier campaign's story, and so do those of a campaign reached only through the sequel, such as its own side campaign.
  - **Why the rule reads the link lines.** A member's label comes from whichever path reaches it first, so a sequel also linked by a shared world is labelled `world`.
  - **Why side campaigns still flow.** A side campaign played alongside the earlier campaign is part of its time, even if it is linked to the sequel too. Folding it at the close is what gets its changes into the sequel's digest.
- **Rejected:**
  - Leaving out only members labelled `sequel`. This was PR #204's first version: a sequel reached by a world link, and a side campaign of the sequel, still flowed back. The open predecessor also stayed a reader that never folds, so the sequel's legacy never dropped a line.
  - Counting only the start's own sequels and what lies beyond them. This was PR #204's third version: from a side campaign played alongside the earlier campaign, the sequel did not count as after its story, so the sequel's legacy could still fold into it and reach that side campaign's own sequel.
  - Stopping at the campaign a candidate continues directly. This was PR #204's fourth version: the fourth review found that a sequel's sequel, linked by a shared world to a side campaign of the first campaign, still counted as alongside it.
  - Treating any campaign a sequel continues as finished, so that it folds and reads nothing, with a close that folds nothing. This was PR #204's second version. The second review found it cut off side campaigns played alongside, both in a predecessor the player kept open (migration 005 allows that after a warning) and at the close, whose fold is how those changes reach the sequel's digest.
  - A `dmc size` flag for the close.
- **Limits:** The rule looks only at links.
  - A side campaign linked only to the sequel counts as after the earlier campaign's story, even if it was played alongside.
  - A campaign that continues one alongside X comes after X, however else it is linked. So two campaigns that name each other on Continues lines (a slip) each come after the other, and no legacy flows between them.
- **Source:** Issue #202; `specs/011-linked-campaigns/` (FR-026, T104, T105); PR #204's four code reviews.

## A module check, and a pointer that names the area (issue #179, Phase C)

- **Date:** 2026-11-14
- **Decision:** A new read-only command, `dmc module check NAME`, reports what keeps `dmc lookup` from printing one area or one entry of an ingested module: a file at the Read cap mark (`Budgets.NearCapTokens`, 20k, or 1,600 lines), a heading whose own text is over a new section limit (`Budgets.ModuleSection`, 3,000), a heading over two or more stat blocks (an AC line followed within eight lines by an HP line), and a heading repeated at the same level under the same parent in one file. It only reports: the fix is an edit to the module's files. `dmc-ingest-module` writes one heading per area, NPC, stat block, item, spell, rule, player option and handout, and runs the check before it reports chapters ready. `dmc size --check` prints one `module:` line while an unfinished module campaign's module fails it, which the resume leaves for the full save. `module-progress.md`'s "Digest to read before continuing" line may name headings (`chapters/NN-title.md § H1; § H2`); the resume reads each with `dmc lookup`, and `dmc size` measures them with lookup's own matcher (`Lookup.FindSection`), so the report is what DMC reads. The older pointer forms keep their meaning. No migration.
- **Reason:** Measured on the maintainer's 638-page module: a resume read the whole hub chapter section (13.8k) where the area is about 2k; three reference files were at the mark (37.3k, 24.1k, 21.8k), so they come back cut when DMC reads one to edit it or after a lookup misses. The module's largest section written one heading per area was 2,428 tokens (p99 1,524), so 3,000 reports none of them and catches a chapter or a monster list under one heading. Its `fateweaving.md` repeats `### PLAYER-SAFE` under every entry on purpose, so a repeat counts only under the same parent. The check is its own command because it is about a module, which campaigns share, not a campaign; play reaches it only through the `dmc size --check` the resume already runs, so play makes no new call. One matcher for lookup and size, because the old "contains, first hit" could measure a different section than the one the resume reads. Report only, because lookup already reaches each stat block, and a tool that rewrites `modules/` would put the player's only digest of a book at risk for a one-time fix (the user's answer in `/speckit-clarify`). The line at resume, because a module ingested before the check would otherwise never be checked (the user's answer).
- **Alternatives considered:** The check in `dmc lookup --check` (lookup's output is a section or a refusal), in `dmc size --module` (size takes a campaign) or in `dmc pdf` (it reads the digest, not the PDF). A section limit of 2,000 (two real single areas over it) or 4,000 and more (lets two or three areas share a heading unseen). Any repeated heading in a file (26 false reports on the real module). A tool that splits a file (more to build, and it writes to the module). Checking only at ingest and on request (old modules never reached). One pointer heading only (loses the scripted event an area depends on).
- **Limits:** A system whose stat blocks print neither AC nor HP relies on the section limit alone. A pointer heading that matches none or several measures the chapter whole and holds the save until it is fixed. No fallback is added for a missing `dmc`: retiring that principle is issue #208.
- **Source:** Issue #179 step 7; `specs/012-large-modules/` (research R0 to R12, FR-001 to FR-018).

  - **No, but.** A party that attacks a major NPC far beyond it, such as Phillip Druskenvald on the train in The Crooked Moon, is stopped by his powers without being killed, and he answers "Oh, I like the spunk" and sets them on the quest.

The maintainer's note that D&D Beyond says improv's "yes, and" can clash with continuity is unverified.

## `dmc` is a required part of DMC (issue #208)

- **Date:** 2026-11-14 (decided while clarifying #179's Phase C, spec 012); clarified 2026-11-17.
- **Decision:** The principle that play never depends on `dmc` is retired. The kit loses its six instructions for working without `dmc`: in `kit/dm-rules.md`, "If `dmc` fails or" before the recall rule and "carry on without dice and maps until then"; in `dmc-draw-map`, `dmc` being unavailable as a reason for a text map; in `dmc-ingest-module`, the fallback to the Read tool's `pages` parameter; in `dmc-setup-rules`, "(Without `dmc`, skip this step.)" and the "Otherwise" before a failed lookup. `dmc` is missing when the shell says the command is not found or the program cannot start. - **Limits:** The start-of-session notice runs under `claude -p` too (checked in the headless run), so DMC knows before its first command; without it, the first command's "command not found" leads to the same stop. A `dmc` that goes missing mid-session is caught only at the next command that fails.

## LF in git, and `dmc` ignoring line endings and the map page, instead of a line-ending migration (spec 018)

- **Date:** 2026-11-17
- **Decision:** `templates/adventures.gitattributes` stores text with LF (`* text=auto eol=lf`), whatever the player's `core.autocrlf`. The checks that compare a campaign with a backup (the restore's warning, the closed-campaign check of `verify` and the sequel) treat a text file whose only change is CRLF against LF as unchanged (`CampaignFiles.SameContent` and `MatchesHash`), and skip the map page files (`CampaignFiles.DerivedFiles`). `dmc map` writes LF on every platform. No migration changes line endings.
- **Reason:** The CRLF files in a campaign come from DMC's own shell writes in play (Python's text mode on Windows), which `kit/dm-rules.md:63` already forbids; a migration would be undone by the next one. With the rules, git stores one style and checks out LF, so without the comparison a clone would fail the closed check and a sequel could not start. The map page is left out of git and drawn again by `dmc redraw`, so on a clone it is missing; the plan missed this, and quickstart Q3 found it on a clone of the maintainer's campaigns. The gitignore's map lines and `DerivedFiles` are kept equal by a test.
- **Rejected:** `* -text` (bytes kept as they are, but a file flipping between CRLF and LF shows as changed in full); no attributes (the player's setting would decide); normalized hashes in `verified.tsv` (old records would still need the raw form); a migration to LF.
- **Limits:** A file whose endings were mixed when a `verified.tsv` was written matches its hash only as it was; the closed check, which compares bytes with bytes, is not affected.
- **Source:** `specs/018-git-friendly-campaigns/` (research R1 to R4 and R7, contract line-ending-compare.md, quickstart Q3).

## A typed resume sets the break baseline (issue #244, spec 019)

- **Date:** 2026-11-18
- **Decision:** When the first resume after a `/clear` or a compaction is DMC's main `Skill` call of `dmc-resume-campaign` (or `resume-campaign`) in the turn of one of the first three player messages, the break baseline is the context of the last call of that turn. A later resume never moves it. A resume before the first player message (the slash command or DMC's call), or a slash resume in the first three turns, is the first resume and keeps the rule of "The break alert is relative to where the resume left the context", as does every other case. The check is a helper beside the shared classifier, not a change to it, and it parses only lines that hold `resume-campaign` with `"assistant"` or `command-name`, or a `\u` escape. The pass over the log classifies every record up to the first resume (the end of its turn) or else the fourth player message, instead of the first. The sheet lines print nothing in a fresh log, one with no reply and no compaction boundary.
- **Reason:** A player who types "Resume campaign." instead of the slash command sends a player message before the resume, so the old rule took the baseline from before the resume and counted the resume as growth. In log `082db04e` the baseline was 37,008, and the break offer came five messages after the resume at about 154,000 tokens, in the middle of a correction; the right first band was about 186,000 (#237). A count of 115 main play logs on 2026-11-18 found the case in 3 (`082db04e`, `6a4e09c3`, `c88dd223`). The same first message printed every present person's sheet lines (up to 10,000 bytes), which the resume then read again.
- **Rejected:** widening the shared classifier (four scans would parse more); a second pass over the log (a second read on every message); the larger of the old and the new baseline (the old one is the low value this replaces); the latest resume of the first three turns, the first version (the code review of PR #271: a typed resume in turn 2 after a slash one moved the baseline from 100,000 to 200,000 and hid the growth); no sheet lines after a compaction too, the first version (it rested on a reload after a compaction that no log shows).
- **Not covered:** a typed message followed by `/dmc-resume-campaign` as the second or third message. The slash command is an echo, not a `Skill` call, so it leaves the baseline at the first reply. The 115 logs hold no such case, and letting the echo set the baseline would let a slash resume early in play lower it (the test `AResumeMidSessionDoesNotMoveTheBaseline`). A resume after a compaction is covered only if DMC reloads with a `Skill` call; no log shows a reload after a compaction, so that is unverified.
- **Source:** Issue #244 (Phase 0 of #238); `specs/019-typed-resume-baseline/`; the code review of PR #271, approved by the maintainer on 2026-11-19.

- **Date:** 2026-11-24
- **Decision:** `review-feedback` holds a cause whose only fix is words (a new or longer sentence in `kit/dm-rules.md`, a skill or a template, a new template field included): its report lists it under "Held until the slip test" and proposes no change; on the user's word it writes `held until the slip test` under the entry's Worker notes once, leaves its status as it is and changes nothing, unless the user lifts the hold for that entry. Not held: a change that removes a contradiction or replaces text without making the file longer (#247, #252 and #261 are of this kind), a mechanism (a hook, a script, a `dmc` check, a deny rule, with the sentence that tells DMC to use it), and a change that replaces a kit rule with a shorter one. A template field counts as words here, although `.docs/development.md` § Writing prompts counts it as a mechanism in general: the hold is about text whose effect has not been measured. The hold ends at the first of: `.docs/roadmap.md` shows the slip test (#249) done, or 2026-12-31; then the held entries are proposed again with their slip-test results, and only those that pass change the kit.
- **Reason:** No measurement shows that the sentences the feedback rounds added decrease slips: the share of player turns that are corrections went from 7.7% before PR #170 to 19.7% after PR #230 (#237; the campaign grew and the player watched more closely in the same period, so this shows no decrease, not harm). `kit/dm-rules.md` grew from 13,581 to 32,510 bytes between 2026-10-12 and 2026-11-17 and is at its cap; entries marked fixed came back (#243); and a sentence PR #230 added (`kit/dm-rules.md:87`) contradicts the line before it.
- **Rejected:** going on as before; a hold with no end date (the slip test may slip, and the player loses small fixes for good).
- **Limits:** The hold applies to the review, not to play; DMC still records feedback the same way. Fewer small fixes reach the player for some weeks. A held change that the slip test cannot run (a rule about pacing, say) is proposed again after the end date with no result, as before the hold.
- **Source:** Issue #248 (Phase 0 of #238); `specs/023-hold-word-only-fixes/`; decision D5 accepted by the maintainer on 2026-11-24.

## The slip test is a C# program that forks real play, scored over fork points (issue #249, spec 024)

- **Date:** 2026-11-24
- **Decision:** The slip test is `slip-test`, a console program in `src/Dmc.SlipTest/` beside `dmc`, built and tested with the solution and never released. A fork-mode replay continues a copy of the play log, rewritten by the runner, with `--fork-session`; the arm's rules go into the log's recorded `CLAUDE.md`, both arms get a rewrite, and the copy's campaign files are restored from Claude Code's file history to the fork's moment. The unit of every interval is the fork point: a bootstrap over points, paired between arms, seed 249. The runs, the pass line and the key are locked by hash before the first run.
- **Reason:** A continued conversation keeps the instructions its log records (#237's pilot), so the log is where a change to the rules has to go; a live probe (spec 024 research R1) showed an edited log is continued and its edit reaches the model. An edit before a thinking block drops that block (R3), which is why the control is rewritten too and the pilot compares thinking between arms. Runs from one base session are not independent and slips come in groups (#240 rule 4), so runs are not the unit. A C# program can be tested in CI on invented logs, which the parsing, the restore and the statistics need; the maintainer writes C#.
- **Rejected:** a PowerShell script beside `tools/recall-test.ps1` (no tests in CI for about ten times its size); a `dmc` subcommand (it would ship to every player); a Wilson interval over runs (treats runs as independent).
- **Limits:** The maintainer's log and file-history format is checked by the pilot, not by the tests: this container keeps no file history for `-p` runs. A dry run here found that Claude Code records the rules without their trailing newline and records them again as changed when the text differs, so the runner records them trimmed; and that the environment notice of a cloud session names a scratchpad folder per session, which a fork always changes. The limits of #249 are in [development.md](development.md#the-slip-test).
- **Source:** Issue #249 (Phase 1 of #238); `specs/024-slip-test-runner/`.

## The slip test restores each file from the backup that holds it at the fork (issue #278, spec 026, a correction of spec 024)

- **Date:** 2026-11-25
- **Decision:** `FileHistory.StateAt` takes, for each file under `adventures/` with a backup after the fork time, the earliest such backup only when no edit of the file falls between the fork and it; otherwise the latest backup at or before the fork, when no edit falls between them. A file with no backup or edit before the fork, whose first edit is a `Write`, did not exist then. Any other case refuses the point, and `run` checks every point before its first model call, so every refused point is named at once. The edits are every `Edit`, `Write`, `MultiEdit` and `NotebookEdit` call the DMC folder's logs record, and each session's first backup of a file (`<stem>@v1`), which no log names, is read from disk.
- **Reason:** Spec 024 research R4 assumed a backup before each turn's first edit, and marked the format not verified. The maintainer's logs show a backup recorded at the next player message and holding the edits before it, no record of `@v1`, and no backup for a file a `Write` creates. In the pilot of #249, one fork saw a session log as it was after play had corrected the slip being replayed.
- **Rejected:** dropping every point with an edit before the next backup (it would drop most points of a session with a save near the fork); rebuilding files by replaying the edit calls (an `Edit` holds only the changed text, and a shell change holds none).
- **Limits:** A change made with a shell command still leaves no backup. The format is that of Claude Code 2.1.317; a later release that records `@v1` is read the same way, because a recorded backup is not added twice.
- **Source:** #249 (the pilot comment of 2026-11-25); `specs/026-slip-test-restore/`; the fix written on the maintainer's computer (branch `fix-slip-test-restore`).

## Development 1 counts bytes, not lines (issue #269, constitution 5.0.0)

- **Date:** 2026-11-25
- **Decision:** Constitution Development 1 counts a plan's cost in bytes added to or removed from `kit/dm-rules.md` and each skill, and in tokens where `dmc size` measures them, not in lines. Its check says the same. A MAJOR amendment (a principle redefined), 4.0.0 to 5.0.0; no other principle changes, and older plans that counted lines stay as records.
- **Reason:** A line is not a unit of cost: one line of `kit/dm-rules.md` can hold 400 characters or more, and a line that gets longer counts as zero. The file grew from 13,581 to 32,510 bytes between 2026-10-12 and 2026-11-17, which a count of lines did not show. Practice already counts bytes (specs 014, 016 and 025; the size cap in `ToolkitTests`), and since #246 (spec 021) `dmc size` gives real tokens.

- **Limits:** Bytes stand in for tokens in the rules and the skills; `dmc size` counts 2 tokens for 5 characters (spec 021). The amendment was drafted from issue #269 and applied on the maintainer's word, not by running `/speckit-constitution`.

## Feedback names the kind of its cause, and only one kind ends in words (issue #266, spec 027)

- **Date:** 2026-11-25
- **Decision:** `review-feedback` § 5 names one of four kinds of cause for each entry, each with the file and line or the log record that shows it (constitution Development 4): (1) the instructions say the wrong thing or contradict each other; (2) a mechanism is missing or cannot do its work; (3) the story files are wrong; (4) the model does not do it reliably, the right line having been in its context. Only kind 1 ends in changed words; it removes or replaces text, and a fix that makes a file longer is proposed as a slip-test trial and changes the kit only if it passes. Kind 2 becomes an issue for a mechanism in the form of a slip-plan trial (#241). Kind 3 is a correction of the data with the player's ruling, and a note on #262 when a step wrote the line. Kind 4 gets no sentence, and counts as evidence for a mechanism. This replaces the hold of spec 023 with a permanent rule.
- **Reason:** The skill found "the cause in the prompts", so every cause was a prompt and every fix was words. Entries marked fixed by words came back: dead time, a character who knows what nobody told it, wrong names, clothing (#243). #237 found that 84% of replies with NPC speech had no lookup, so a rule to look something up does not run when the reply is written.
- **Rejected:** keeping the hold with a later end date (it pauses the loop but does not change it); no words ever (a contradiction in the rules is a real cause that only words can fix).
- **Limits:** The kind is the reviewer's reading of the evidence. Telling kind 4 from kind 2 needs the log, which the digest gives; without it the skill names no kind and says what it would need to read. The hold of spec 023 ended when `.docs/roadmap.md` showed the slip test done (PR #275), so this rule takes over from it with no gap.
- **Source:** Issue #266 (Phase 4 of #238); `specs/027-cause-kinds/`; decision D5 of #238 and spec 023.

## "Fixed" means the slip stopped (issue #267, spec 028)

- **Date:** 2026-11-25
- **Decision:** A feedback entry moves from `filed #N` to `released in X.Y.Z` once its PR has merged, states its slip-test result or why it has none, and a release holds it. It becomes `fixed in X.Y.Z: no case in N play turns` only when the story sessions on that release or later have at least 300 play turns, as `review-transcript` § 7 counts them, with no case of its fault. An entry whose fault comes back after released or fixed is `open` again: `dmc-record-feedback` and `review-transcript` search those statuses too, and start the occurrence "came back after <the status>". An older `fixed in PR #N` is read as released.
- **Reason:** "Fixed in PR" meant a change was made, and entries marked fixed came back (#267: dead time, knowledge, names, clothing). Zero cases in 300 turns puts the fault below 1 in 100 turns with 95% confidence (the rule of three), a quarter of the 4.7 slips per 100 turns of #250's baseline.
- **Rejected:** a rate test against the rate before the release (an entry's occurrences give no count of the fault before it); a new entry for a slip that came back (it starts from zero, which is what hid the failed fixes); a migration of old entries (the skills read the old word).
- **Limits:** A fault rarer than 1 in 100 turns can still pass when it was never fixed: the condition shows the fault is rare, not gone. Whether a slip is "the entry's fault" is the reviewer's judgment.
- **Source:** Issue #267 (Phase 4 of #238); `specs/028-fixed-condition/`; #250's baseline; spec 025.

## A PR that changes play states its slip-test result (issue #268, constitution 5.1.0)

- **Date:** 2026-11-26
- **Decision:** A PR that changes how DMC plays (`kit/dm-rules.md`, a kit skill, a kit hook or its output, a kit template, or `kit/settings.json`) states its slip-test result: the fork points or play sessions, the number of runs, the pass line fixed in its issue before the run, and the result against a control run at the same time. Constitution 5.1.0 (MINOR) points at it from § Development Workflow, and the Spec Kit task template has a line for it.

- **Rejected:** a PR template (the repository has none, and the rule would have two homes); requiring a run for every change (a document or a test changes no reply).

PRs merged before 2026-11-26 need no statement, the cutoff `review-feedback` § 2 already uses for a filed entry (spec 028). Applied on the maintainer's word from a reviewed draft, not with `/speckit-constitution`.

## A wardrobe and keepsakes section on sheets (issue #286, spec 030)
